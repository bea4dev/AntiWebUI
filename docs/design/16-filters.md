# 16. filter、ブラー、backdrop

[14](14-shaders.md) の「箱の中を塗る」に続いて、描いた内容や背後を入力にする段を足す。

## API

組み合わせは「画像の式」で書く。手でパスとテクスチャを組む API にはしない。ピクセルがどこまで離れた入力に依存するかをフレームワークが知らないと、差分描画を保てないため。

```rust
// 組み込みのブラーはスタイル。hover や transition が効く
div().blur(4.0);
div().rounded(12.0).bg(rgba(0xffffff18)).backdrop_blur(20.0)
    .transition(Transition::ms(200))
    .hover(|s| s.backdrop_blur(32.0));

// 自分と子を描いた結果に掛ける
div().filter(move || {
    let mut img = Image::content();
    if soft.get() { img = img.blur(radius.get()); }
    if crt.get()  { img = img.through(&CRT, Crt { line: 3.0 }).reach(2.0); }
    img
});

// 背後を入力にして箱の中を塗る。枝分かれしてもよい
div().fill(move || {
    let back = Image::backdrop();
    let frosted = back.clone().blur(18.0);   // clone は結果の共有で、計算は 1 回
    LIQUID.params(Liquid { bend: bend.get() })
        .inputs([back, frosted])
        .reach(48.0)                         // 最大 48 論理 px 離れた場所まで読む
});

// 文字の形の影
div().filter(move || {
    let me = Image::content();
    let shadow = me.clone().blur(6.0).through(&TINT, Tint { color: rgb(0x000000) });
    OVER.params(()).inputs([shadow, me])
});
```

```wgsl
fn paint(f: Frag) -> vec4<f32> {
    let dx = sin(f.px.y * 0.05 + params.time) * params.amp * aw_box.scale;
    return read0(f.px + vec2<f32>(dx, 0.0));   // 入力は箱の座標で読む。read0 〜 read3
}
```

| | 内容 |
|---|---|
| `Image::content()` | 自分と子を描いた結果。`filter` の中だけで意味を持つ |
| `Image::backdrop()` | 背後。`fill` と `overlay` の中だけで意味を持つ |
| `.blur(r)` | ぼかす。`r` は CSS の `blur(r)` と同じく標準偏差で、論理ピクセル |
| `.through(&SHADER, params)` | この画像を入力 0 にしてシェーダーを通す |
| `SHADER.params(p).inputs([...])` | 複数の入力（最大 4 つ） |
| `.reach(r)` | シェーダーが入力を読む最大距離（論理ピクセル）。`filter` では外へはみ出す距離にもなる |

- 自分の `f.px` は箱の左上からの物理ピクセルのまま。`filter` では箱の外の負の値も来る。
- `reach` より外を読むと、範囲の端の色になる。テクスチャの外のゴミは読まない。
- `filter` の中の `backdrop()` と `fill` の中の `content()` は透明になる。

## 見える範囲

| 場面 | 結果 |
|---|---|
| スクロール内容の上に固定したヘッダー | 正しく動く。スクロール中はヘッダーの読む範囲だけ計算し直す |
| 同じ要素の `backdrop_blur` と `scale` / `rotate` / `opacity` | 正しく動く |
| 親がスクロール、`transform`、`opacity`、`filter` のレイヤー | **そのレイヤーの中身しか見えない**（合意済みの制限） |
| ポップアップから、その下のウィンドウ | 見えない（別サーフェス） |
| ウィンドウの後ろのデスクトップ | 見えない（`ext-background-effect-v1` が要る。後回し） |

自作シェーダーの `fill(Image::backdrop())` は、同じ要素に変形があるとレイヤーの中身しか見えない。背後を変形の外から読めるのは組み込みの `backdrop_blur` だけ。

## Chromium との違い

Chromium の `backdrop-filter` は要素の箱の外を読まず、端を鏡映しにする。こちらは**箱の外も読む**（KWin や macOS と同じ）。隣の色が自然に回り込み、動かしたときに端が目立たない。代わりに、箱の外の変化でも計算し直す。ウィンドウの端では端の色を延ばす。

## 方式

### ブラー: Dual Kawase

縮小を繰り返してから拡大で戻す。半径が大きくなっても段数が増えるだけで、コストは読む範囲の面積に対してほぼ頭打ちになる。

KWin は半径の変化をサンプルのオフセットで作るが、シミュレーションではオフセットが整数以外のときに格子模様と中心のずれが増えた（ガウスとの L1 誤差、4 段で `d = 1` が 0.079、`d = 1.5` が 0.214、`d = 2.5` が 0.234）。そこで**オフセットは 1 に固定し、段の間を混ぜてつなぐ**。

| 段（縮小の回数） | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 標準偏差 σ（テクセル） | 1.68 | 3.76 | 7.71 | 15.5 | 31.1 | 62.2 | 124 | 249 |

`σ_L ≤ σ < σ_{L+1}` のとき、`L + 1` 段まで縮小する。最初の拡大の結果（`L` 段の大きさ）に、縮小の途中の `L` 段を混ぜる。

```
t = (σ² - σ_L²) / (σ_{L+1}² - σ_L²)
結果 = mix(縮小の L 段, 拡大の結果, t)
```

分散が σ² に一致し、`t = 0` と `t = 1` でそれぞれの段の結果そのものになるので、半径を連続に変えても見た目が跳ねない。拡大 1 回に 1 タップ足すだけで済む。249 より大きい σ は 249 として扱う。

**`σ ≤ 1.68` は縮小しない。** 縮小を 1 回挟むだけで σ 1.68 になるので、これより小さい半径は作れない。元の画像との混合は段差の中に鋭い芯が残る（実測で `blur(1.0)` の 16〜84% の幅が 0 になった）。そこで等倍のまま縦横 2 パスのガウスを計算する（最大 15 タップ）。

実測のガウスとの差（段差の応答の最大誤差。黒と白の段差で 1 が全幅）: σ 0.5 は 5.3%、σ 1〜50 は 0.5〜3.4%。

読む範囲は `3σ`。その外の重みは 0.3% 未満なので切り捨てて、範囲の端の色を延ばす。

範囲の左上を縮小の格子（`2^段数`）に揃える。これで箱が動いても、動かない背景に対する格子が変わらず、ぼかした結果がちらつかない。

### 式の評価

| 入力 | 取り方 |
|---|---|
| `content` | レイヤーのテクスチャから必要な範囲をコピーする。周りは透明 |
| `backdrop` | 描画先の、そこまで描いた結果をコピーする |

1 回の評価の手順:

1. 式を根から順にたどり、各段に必要な範囲を求める（`clone` で共有した段は和を取る）。
2. 葉から順に、プールの中間テクスチャへ描く。
3. 結果は、`fill` ならそのまま箱の形に切って描き、`filter` ならレイヤーごとに持つ出力テクスチャに入れる。

中間テクスチャはプールで使い回す。縮小の段は使い終わったらすぐ返すので、同じフレームの別の評価でも使える。8 フレーム使わなかったものは解放する。

`filter` の結果は次に変わるまで保持する。背後の変化などで親だけが描き直されても、ぼかし直さない。内容か式が変わったときは、見えている範囲全体を計算し直す（変更された部分だけの再計算は今回やらない）。

### レイヤー

`filter` または `blur` を持つノードはレイヤーになる。座標の空間は `opacity` のレイヤーと同じく変えない。

- `Layer::filter` に式と箱の値を持つ。`bounds` は内容の範囲を `reach` だけ広げたもの。
- 内容の変更は `reach` だけ広げて親の変更矩形にする。
- `filter` と `blur` のパラメータだけが変わるフレームは内容を描き直さない。親のレイヤーだけを描き直す。
- CSS と同じく stacking context を作る。

### backdrop: 描画の分割

backdrop を読むプリミティブの位置で描画を区切る。

```
区間 0 を全矩形に描く → そこまでをコピーしてブラーなどを計算 → 区間 1 を全矩形に描く → ...
```

矩形ごとに区間を繰り返すと、他の矩形がまだ描かれていない状態を読んでしまうので、区間が外側のループになる。backdrop が無いシーンでは区間は 1 つで、これまでと同じ描画になる。

### 変更矩形の拡張

変更が読む範囲に掛かったら、**読む範囲全体を変更矩形に足す**。

- 箱の中身が変わるので、箱は描き直しが要る。
- 背後を読むには、読む範囲を要素より手前のものを除いて描き直す必要がある。今のバッファには前のフレームの手前の要素まで残っている。

足した範囲がさらに別の backdrop に掛かることがあるので、変わらなくなるまで繰り返す。読む範囲に変更が掛からなければ追加のコストは無い。

拡張は `damage::diff` で行うので、コンポジタに伝える範囲にも入る。レイヤーの中でも `diff_content` で同じように働く。レンダラも受け取った矩形（古いバッファの分を足したもの）に同じ拡張を掛ける。

読む範囲は箱の位置だけで決まり、変更矩形に依存しない。したがって部分描画と全面描画の結果は一致する。

### 描画先

**backdrop を読むシーンでは、ウィンドウをサーフェスと同じ大きさの中間テクスチャ（キャンバス）に描き、変更矩形だけをサーフェスへ写す。**

相談の時点では、描画先からの直接コピーを基本にして、できない環境だけ中間テクスチャにする案だった。実装を見て変えた。
| | 直接コピー | キャンバス（採用） |
|---|---|---|
| 必要な機能 | dmabuf とサーフェスの `COPY_SRC`。修飾子によっては付けられない | なし |
| 経路 | 直接コピーと代替の 2 本 | 1 本 |
| GPU | コピーのみ | 変更矩形の描画が 1 回増える |
| メモリ | 中間テクスチャのみ | ウィンドウ 1 枚分（1620×1616 で約 10 MB） |

backdrop が無いシーンではキャンバスを持たない。持っていないときに backdrop が現れたら、そのフレームは全面を描く。レイヤーのテクスチャは自前なので、そこからコピーする。

### 同じ要素の変形と不透明度

`backdrop_blur` は `Primitive::Backdrop` として親のシーンに置く。レイヤーの直前に、レイヤーと同じ行列と不透明度を持つ。専用のパイプラインで、画面の位置からブラーの結果を読み、箱の座標で角丸を計算する。

順番は CSS と同じく、自分の影より前。自分の影を背後として読まない。

## パイプラインの作成

ブラーと backdrop のパイプラインは最初に使うフレームで作る。使わないアプリの起動を遅くしない。

## 性能

2026-11-04。RTX 5070 Laptop（コンポジタも NVIDIA）、ShojiWM、120 Hz、スケール 1.8、900×900。電源接続。`bench_filters`（文字と図形の上で 400×240 論理のパネル、半径 20）と、同じ構成を CSS の `backdrop-filter` / `filter` と `requestAnimationFrame` で書いたページを交互に 2 回。起動後 4 秒を除いた 7〜8 秒。CPU は 1 コアを 100% とし、Chrome は全プロセスの合計。

| 負荷 | AntiWebUI CPU | Chrome CPU | フレームの CPU（ms） | 記録から GPU 完了（ms） |
|---|---|---|---|---|
| 効果なしのパネルが動く | 6.9〜7.1% | 21.6〜22.5% | 0.46 | 0.30 |
| backdrop のパネルが動く | 11.2〜12.2% | 19.8〜20.4% | 0.90 | 0.56 |
| 背後が動く | 9.9〜10.2% | 23.3〜24.6% | 0.68 | 0.50 |
| 読む範囲の外で何かが動く | 7.6〜8.2% | 21.0〜21.6% | 0.51 | 0.31 |
| 2000 行のスクロールの上のヘッダー | 15.3〜16.6% | 20.3〜23.2% | 1.19 | 0.68 |
| `blur` の半径が変わる | 10.6〜12.3% | 23.1〜23.4% | 0.76 | 0.50 |
| `blur` のカードが動く | 10.6〜11.1% | 24.9〜26.3% | 0.72 | 0.30 |
| `blur` のカードの中身が変わる | 9.9〜10.1% | 24.5〜26.4% | 0.71 | 0.55 |

- どれも飛ばしは問題にならなかった。AntiWebUI の fps は 114〜120 で、整数に丸めると動かないフレームは描かないため（`left` のサイン波の折り返し）。Chrome の fps は `requestAnimationFrame` の回数で 120。
- **読む範囲の外で動くものには追加のコストが無い**（効果なしと同程度）。
- **`blur` のカードが動くときは再計算しない**ので、GPU は効果なしと同じ。
- NVIDIA の電力はコンポジタが支配的で、多くの負荷で 22〜24 W、Chrome との差は 1.5 W 以内。例外はスクロールの上のヘッダーで AntiWebUI 27.7〜27.8 W、Chrome 23.2〜23.6 W。ただしブラーなしのヘッダーでも約 25 W（1 回の測定。もう 1 回は起動直後の状態が混ざって外れ値だった）なので、ブラーの上乗せは 1〜3 W で、差の多くは元のスクロールのものと見ている。
- Chrome のページは比較用に書いたもの。Chrome の `backdrop-filter` は箱の外を読まないので、読む範囲が AntiWebUI より狭い。

### 半径とコスト

全面描画 1 回あたり（1620×1620、400×240 論理のパネル、オフスクリーン、読み戻しを含むので差を見る）。

| ms | backdrop なし | 半径 2 | 8 | 20 | 60 |
|---|---|---|---|---|---|
| RTX 5070 Laptop | 3.64 | 3.78 | 3.75 | 5.36 | 6.09 |
| Radeon 880M | 1.61 | 1.61 | 1.65 | 2.59 | 2.86 |

実ウィンドウで半径 2、8、60 のパネルを動かすと、フレームの CPU は 0.68、0.85、1.16 ms。パネルが増えるとほぼ比例する（小さいパネル 8 枚が 1.71 ms、記録から GPU 完了が 1.40 ms）。

内蔵 GPU でアプリだけ描いた場合（コンポジタは NVIDIA のまま）、背後が動く負荷のフレームの CPU は 1.03 ms、fps は 117。

### 初回

ブラーと backdrop のパイプラインを作るフレームは、ドライバのキャッシュなしで NVIDIA +約 36 ms、Radeon +約 8 ms、ありで約 +2 ms（各 3 回）。プロセスで 1 回。`Shader::preload` に当たる API は用意していない。モーダルの初回で気になるようなら足す。

### メモリ

`backdrop` のあるシーンはウィンドウ 1 枚分（1620×1620 で約 10.5 MB）のキャンバスと、読む範囲の大きさの中間テクスチャを使う。中間テクスチャは 8 フレーム使わなければ解放する。`filter` はレイヤーと出力で、読む範囲の 2 枚分。

**未計測:** 内蔵 GPU をコンポジタの出力にした状態と 60 Hz。
