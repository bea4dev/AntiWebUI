# 25. パス描画とインライン SVG

任意の形を描く `Primitive::Path` と、形をノードとして持つ `svg` を追加した。`img("logo.svg")` は今までどおり 1 枚の絵として描く（[22](22-images.md)）。

Markdown エディタの Mermaid のような、箱と線が数百から数千ある図を想定して、形の準備と保持を軽くすることを優先した。

## 使い方

```rust
svg().w(200.0).h(100.0).view_box(0.0, 0.0, 24.0, 12.0).child(
    svg::group()
        .fill_none()
        .stroke(Color::BLACK)                  // 子へ継承される
        .child(svg::path("M2 2 C 8 12, 16 0, 22 10").stroke_width(0.5))
        .child(
            svg::circle(12.0, 6.0, 4.0)
                .fill(Gradient::radial(0.5, 0.5, 0.5).stop(0.0, Color::WHITE).stop(1.0, c))
                .hover(|s| s.fill(Color::WHITE))   // 状態のスタイルも使える
                .on_click(|_| {}),                 // 塗られた部分だけに当たる
        )
        .child(svg::text("label").at(12.0, 6.0).anchor(svg::TextAnchor::Middle)),
)

// 形が変わるものはクロージャで渡す
svg::path(move || star(angle.get()))

// SVG ファイルも同じノードになる
svg::parse(bytes)?

// 図を組み立てる前に文字の大きさを測る（Mermaid のラベルなど）
svg::measure_text("label", &Style::default().text_size(14.0))
```

形は普通のノードなので、シグナル、`for_each`、`dyn_view`、`hover`、`transition`、イベント、カーソルがそのまま使える。`view_box` がなければ座標は論理ピクセルになる。

| CSS / SVG | ここ |
|---|---|
| `fill` / `stroke`（`currentColor`、グラデーション） | `.fill()` / `.stroke()`、`.fill_current()` |
| `fill-opacity` / `stroke-opacity` / `stroke-width` | 同じ名前 |
| `fill-rule` / `stroke-linecap` / `stroke-linejoin` / `stroke-miterlimit` | `.fill_rule()` / `.line_cap()` / `.line_join()` / `.miter_limit()` |
| `stroke-dasharray` / `stroke-dashoffset` | `.dash_array()` / `.dash_offset()` |
| `vector-effect: non-scaling-stroke` | `.non_scaling_stroke()` |
| `transform` 属性 | `.transform()`、`.dyn_transform()` |
| `preserveAspectRatio` | `.aspect(SvgAspect)` |

`fill` は `div` では今までどおりシェーダーの `.fill(closure)` である。`Style` と形では色を受け取る。

## 大きさ

`svg` の大きさは Chromium で測った結果に合わせた（`anti-webui-core/tests/svg.rs`）。

| 指定 | 結果 |
|---|---|
| なし | 300×150 |
| `view_box` のみ | 使える幅いっぱい、高さは比から |
| 幅のみ | `view_box` があれば比から、なければ高さ 150 |
| 高さのみ | `view_box` があれば比から、なければ幅 300 |

## 描き方

候補を比べて、CPU で形の覆う範囲を疎に求め、GPU で塗る方式にした。

| 方式 | 長所 | 短所 |
|---|---|---|
| 形全体をマスクにする | 単純 | 対角線 1 本でも箱全体のメモリが要る |
| 三角形に分割して MSAA | 大きな形に強い | 別の描画先が要り、Chromium と縁を揃えにくい |
| `vello_hybrid` | 考え方は同じ | wgpu 29 に依存していて、こちらの wgpu 30 とデバイスを共有できない |
| **疎な帯（採用）** | メモリが輪郭の長さに比例し、縁が正確 | 形が毎フレーム変わると CPU を使う |

Skia も、小さいパスはアトラス、それ以外は別の経路と使い分けていて、形を毎回 GPU で解くわけではない。

### 手順

```
BezPath ── 線なら kurbo で輪郭の形に ── 変換して折れ線に（誤差 0.05 px）
    ↓
セル: 線が通る画素だけ「ここから右を覆う量」と「この画素の面積」を持つ（FreeType や AGG と同じ）
    ↓
帯: 4 行ごとに、セルがある範囲の画素だけ覆う量を保存。間は行ごとに覆う量が一定の矩形
    ↓
インスタンス: 位置、大きさ、保存先、描画の番号の 20 バイト
```

- 40×40 px に収まる形は帯に分けず 1 ブロックにする。アイコンは 1 インスタンスで済む。
- 帯をまたいで同じ矩形は 1 つにまとめる。大きな矩形の内側は 1 インスタンスになる。
- 新しい形が 48 個以上あるフレームは、全コアで作る（最大 8 スレッド）。ユーザーのコードには見えない。
- 8192 px を超える形は、見えている範囲だけ作る。

### GPU 側

WebGL2 相当の制限で動かしているので、ストレージバッファは使わない。

- **覆う量:** 幅 2048 の R8 テクスチャを 1 次元の配列として使う。追加のみで、埋まったら全部捨てて作り直す。1 フレームに必要な量が大半なら、捨てずに広げる。
- **描画ごとの情報:** 色、クリップ、グラデーションを `Rgba32Float` のテーブルに毎フレーム書く。インスタンスを小さくするためである。
- **結果の再利用:** 形の ID と行列の小数部分、線の指定、ルールをキーにする。整数ピクセルの移動では作り直さない。

グラデーションはフラグメントシェーダーで計算する。SVG どおり、色は乗算前のまま補間する。

### テキスト

`svg::text` の中身は普通のテキストノードで、登録したフォントが使え、選択もできる。周りの拡大率を掛けた大きさで整形し、`fill` の色で塗る。

ヒットテストは形に正確に当たる。塗りは巻き数で、線は線分までの距離で判定する。`g` と `svg::text` の枠自体には当たらない。

## SVG ファイル

`svg::parse` は `usvg` で読んで、同じノードに変換する。`<use>`、`<marker>`、`<style>`、単位の解決は `usvg` がする。

矩形の `clip-path`（`<marker>` の箱もこれになる）は、輪郭を CPU で切り取る。回転した矩形でもよい。それ以外の `clip-path`、パターン、マスク、フィルタ、画像、ブレンドのどれかがあると、全体を今までの `img` の経路で 1 枚の絵にする。ラベルはその上に重ねる。

### `foreignObject`（Mermaid のラベル）

Mermaid のフローチャートは、ラベルを `<foreignObject>` の中の HTML で書く。ブラウザ以外の多くの SVG 実装（`usvg`、KolourPaint の Qt SVG）は HTML を解釈しないので、文字が消える。Mermaid を描くのが目的の 1 つなので、ここで対応した。

1. `roxmltree` で `foreignObject` を探す。`<style>` の規則（`simplecss`）、`style` 属性、継承から、色、フォント、大きさ、太さ、`text-align`、`line-height`、`white-space`、背景色を求める。
2. その場所を目印の透明な `<rect>` に置き換えて `usvg` に渡す。周りの `transform` や非表示の扱いは `usvg` がする。作者の CSS が目印に効かないよう、`style` 属性で固定する。
3. 変換後の木で目印を見つけて、背景の矩形と `svg::text` に置き換える。

HTML 全体を解釈するのではなく、文字と背景だけを取り出す。1 つのラベルは 1 つのスタイルで、途中で色や太さが変わるものは最初の文字のスタイルになる。

### `<text>`

`usvg` は文字を輪郭に変換して、独自のフォント選択をする。そのため、1 チャンク 1 スパンの単純な `<text>` は `svg::text` に置き換える。アプリの他の文字と同じフォントになり、選択もできる。文字ごとの回転、パスに沿った文字、下線、線付き、1 チャンクに複数のスタイルがあるものは、輪郭のままにする。

点に置く 1 行の文字だけの `<text>`（`tspan` の入れ子と `x`、`y`、`dy` を含む）は、`usvg` に渡す前に取り出して目印の矩形に置き換え、`svg::text` にする（[28](28-markdown.md) の「SVG の文字」）。`usvg` に組ませるとシステムのフォントを全部読み込むので、それを避けるためである。読み込むのは、そうできない `<text>` が残るときだけになる。読み込んだフォントはプログラムで 1 つだけ持ち、どのスレッドの `svg::parse` と画像の SVG も同じものを使う。

### 属性の一部で選ぶセレクタ

`usvg` のスタイルシート（`simplecss` 0.2）は `[name^=v]`、`[name$=v]`、`[name*=v]` を知らず、そのセレクタを含む規則を、並んだ他のセレクタごと捨てる。Mermaid は矢じりの `<marker>` を `[id$="-extensionEnd"]` で選ぶので、`usvg` に渡す前に、ファイルの中でそれに当たる値ごとの `[name="…"]` に書き換える。当たる値が無いセレクタは消し、全部が消えた規則も消す。こういうセレクタが無いファイルは、そのまま渡す。

`dominant-baseline` は `middle`（x-height の半分）と `central`（ascent と descent の中間）を区別する。どちらも、文字がフォールバックのフォントでも、リストの最初のフォントの値を使う。

### フォントの代役

`font-family: arial` は、Arial がなくても Chromium では fontconfig の別名で Liberation Sans になる。fontique はこの別名を見ないので、次の名前（多くは既定の sans-serif）に進み、見た目が大きく変わっていた。`text/mod.rs` の `STAND_INS` で、リストの名前の直後に同じメトリクスのフォントを足す。`anti-webui` のすべての文字に効く。

### 実際のファイルで確かめたこと

Mermaid のフローチャートとシーケンス図の実ファイルで、文字の位置を Chromium と比べた。ラベルは一致した。`middle` の文字も一致した。`central` の文字だけ、1 px 上にずれる。原因は分かっていない。

## Chromium との比較

`tools/svg_compare.py` で、`tests/data/svg` の 12 ファイルを GPU ラスタの Chromium と画素で比べた。差は RGB で最大のチャンネルの差（0〜255）である。

| ファイル | 1.0 倍の平均 | 1.0 倍の最大 | 1.8 倍の平均 | 1.8 倍の最大 |
|---|---|---|---|---|
| dashes | 0.044 | 56 | 0.047 | 51 |
| fill-basic | 0.044 | 30 | 0.025 | 32 |
| gradients | 0.116 | 17 | 0.105 | 50 |
| opacity | 0.016 | 1 | 0.017 | 23 |
| rules | 0.109 | 134 | 0.059 | 112 |
| strokes | 0.121 | 69 | 0.068 | 104 |
| subpixel | 0.073 | 57 | 0.043 | 64 |
| thin | 0.061 | 25 | 0.021 | 51 |
| tiger-ish | 0.268 | 77 | 0.266 | 79 |
| transforms | 0.016 | 13 | 0.009 | 15 |
| use-marker | 0.056 | 86 | 0.071 | 77 |
| viewbox | 0.017 | 57 | 0.008 | 21 |
| **文字のないファイル全体** | **0.079** | | **0.062** | |
| mermaid-labels | 1.708 | 204 | 1.735 | 204 |

最大の差は縁の数画素で出る。`mermaid-labels` の差は主に文字の描画で、位置は合っている（文字のアンチエイリアスは [04](04-text.md) の方式で、Chromium とは異なる）。`rules` は自己交差する星の交点である。セル方式は 1 画素の中で辺が交わるときの覆う量が近似になる。

## 性能

箱と曲線と文字の図（`examples/bench_svg.rs`、`tools/svg_bench.py`）を、Radeon 880M、1728×1616 相当で測った。図全体が画面に入る大きさで、すべて描画される。

| 箱の数 | 表示までの合計（AntiWebUI） | 表示までの合計（Chromium） | PSS（AntiWebUI） | PSS（Chromium の全プロセス） |
|---|---|---|---|---|
| 300 | 67 ms | 76〜92 ms | 164 MiB | 556 MiB |
| 1000 | 123 ms | 136〜140 ms | 204 MiB | 570 MiB |
| 3000 | 279 ms | 188 ms | 328 MiB | 603 MiB |

- AntiWebUI の合計は、ビューの構築、レイアウト、ペイント、最初のフレームの GPU 完了までである。Chromium の値は同じ内容のページの `first-contentful-paint` である。起動時間はどちらも含まない。
- 測り方が同じではないので、差が小さい行は同等と見るのが妥当である。AntiWebUI は窓なしで測った。
- 3000 では Chromium より遅い。レイアウトの 114 ms の大半が文字の整形である（文字 1 つあたり約 28 µs）。最初の 30 ms ほどはフォントの読み込みで、箱の数によらない。

内訳（箱 1000、ms）:

| 構築 | レイアウト | ペイント | 最初のフレームの CPU | GPU 完了まで | 全部描き直し（CPU） | 1 つの色を変える（木とペイント + CPU） |
|---|---|---|---|---|---|---|
| 15 | 57 | 2 | 40 | 49 | 8〜11 | 4.2 + 1.5 |

全コアで作る前は、最初のフレームの CPU が 141 ms だった。

色を 1 つ変えるときの負担は、シーン全体のペイントと比較がほとんどである。箱 3000 だと 12 ms + 5 ms で、120 Hz の 1 フレームを超える。

## やっていないこと

- 手での確認。実ウィンドウでの表示は確かめたが、操作は合成イベントだけで確かめた。
- 回転や傾きのある `svg::text`。大きさと位置は追うが、文字は回転しない。
- `svg::text` の線、1 つのテキスト内の `tspan`。
- `paint-order`、`<pattern>`、`<mask>`、`<filter>`、`<image>`、ブレンド、矩形以外の `clip-path` をノードのまま描くこと（`parse` は全体を絵にする）。
- ヒットテストと `svg::text` に矩形の `clip-path` を効かせること。
- `foreignObject` の HTML の一般的な解釈。1 ラベル 1 スタイルで、画像やレイアウトは無視する。
- `width="100%"` と CSS の `max-width` の解釈。`parse` は `viewBox` の大きさにするので、変えるなら `.w()` と `.h()` で指定する。
- CSS の `clip-path` と `mask-image` を普通のノードに使うこと。`Primitive::Path` が土台になる。
- `img` の SVG の `currentColor`、アプリのフォント、解析結果のキャッシュ。
- SMIL と SVG 内の CSS アニメーション。
- 形が毎フレーム変わるときの保存先の節約。古い形は保存先が埋まるまで残る。
- 色を 1 つ変えるときの負担を箱の数に比例させないこと。
- Chromium の 1 操作ごとの応答時間との比較、内蔵 GPU 以外、60 Hz、バイナリサイズの増分。
