# 29. content-visibility（見えない所を後回しにする）

長い文書を開くとき、見えていない段落まで文字を整形すると、時間のほとんどがそこに使われる（[28](28-markdown.md) の「速さの確かめ方」では、48 KB の Markdown のレイアウト 40 ms のうち 29 ms が整形だった）。CSS の `content-visibility: auto` と同じく、画面から遠い要素は中身をレイアウトせず、大きさだけを決めておく。

## API

```rust
div()
    .content_visibility_auto()         // CSS の content-visibility: auto
    .contain_intrinsic_height(400.0)   // CSS の contain-intrinsic-height: auto 400px
div()
    .content_visibility_auto()
    .estimate_contents()               // 独自: 中身の文字を整形せずに見積もる
div().content_visibility_hidden()      // CSS の content-visibility: hidden
```

- `content_visibility_visible()` が既定。
- `contain_intrinsic_size(w, h)`、`contain_intrinsic_width(w)` もある。論理ピクセル。

## 中身を飛ばすとき

`hidden` は常に、`auto` は「関わりがない」ときに中身を飛ばす（skip）。

- 中身はレイアウトも描画もされず、当たり判定も受けない。
- 中身のノードは `visible` が偽になる。ただし文書の順番（`doc_order`）は振っておくので、選択の前後の比較は正しいままになる。
- 箱の大きさは次の順で決める。
  1. 覚えている大きさ: 最後に中身をレイアウトしたときの大きさ。幅の条件（親から決められた幅、使える幅、パーセントの基準）が同じときだけ使う。CSS の `contain-intrinsic-size: auto` に当たるが、ここでは常に有効にする。
  2. `estimate_contents` があれば見積もり（下）。
  3. `contain_intrinsic_*` の値。
  4. 何もなければ中身がないものとして、パディングとボーダーだけ。CSS と同じ。
- スタイルの解決は飛ばさない。

### 関わりがあるとき（`auto`）

CSS の仕様と同じく、次のどれかなら中身をレイアウトする。

- 画面に近い: 箱を、ウィンドウの幅と高さの半分ずつ四方に広げると、切り取られた残りがウィンドウにかかる。スクロールする要素の中なら、その見えている範囲も同じように見る。Chromium も画面の外にある程度の余裕を取っている。
- フォーカスを持つ要素が中にある。
- 選択の一部が中にある（範囲の両端の `doc_order` で比べる）。
- `scroll_into_view` の行き先が中にある。

新しく作った要素は「関わりなし」から始める。最初の位置決めのあと、同じ `update` の中で判定し、変わった要素だけをレイアウトし直す。最初の絵が空になることはない。スクロールしたときも判定する。判定は `auto` の要素の一覧だけを見るので、ノード全体は回らない。

### スクロールが跳ねないようにする（scroll anchoring）

見積もりと本当の大きさは違うので、ほかの要素が関わりありになると、見えている所が動いてしまう。そこで CSS の scroll anchoring と同じく、目印の要素を決めて、それが画面の同じ所に残るようにスクロール位置を動かす。

- 関わりが変わる要素があったら、それをスクロールする要素ごとに、目印を 1 つ選ぶ。目印は、中身がレイアウトされている `auto` の要素のうち、その見えている範囲にかかる、文書の順でいちばん前のもの。
- 目印が中身の上端から何ピクセル下にあるかを、前のレイアウトの `rect` から求めておく。レイアウトし直したあと、位置を決める前にもう一度求め、変わった分だけスクロール位置を動かす。
- 最初は「見えている範囲より丸ごと上にある要素の分だけ直す」つもりだった。これでは、見出しへ飛んだあとに見えている範囲の中で要素が本当の大きさになる場合や、余裕より大きくスクロールして要素が途中まで見えてから関わりありになる場合に、ずれが残った（テストの `what_shows_does_not_jump`、`scrolling_to_something_skipped_lays_it_out_first`）。

関わりなしに戻るときは、覚えている大きさ（いまの大きさと同じ）を使うので、何も動かない。

### `scroll_into_view`

行き先が飛ばされた要素の中にあると、その位置はまだない。そこで、外側の飛ばされた要素を関わりありにしてレイアウトし直し、そのあとで行き先へスクロールする。Markdown の見出しへのリンクがこれを使う。

## 見積もり（`estimate_contents`）

覚えている大きさがないとき、中身を「文字を整形しない」モードで測る。箱、フレックス、余白はふつうに計算し、文字だけを次のように見積もる。

- フォントの指定、大きさ、太さ、スタイル、行の高さごとに、英数字の見本を 1 回だけ整形して、1 文字の平均の幅と 1 行の高さを覚える。
- CJK などの全角の文字は 1 em とする。
- 折り返す文字は、改行ごとの行について、幅を「使える幅から平均 3 文字を引いた幅」で割って切り上げた行数にする。単語の途中で折り返せない分の目安である。
- 段落の中のインラインの箱（画像、絵文字）や、大きさの違うスパンは数えない。

見積もりは測るだけなので、測った結果のキャッシュには入れず、何も書き換えない。見積もった大きさは、その要素の `estimated` に幅の条件と一緒に置いておき、中の何かが変わる（`invalidate_layout`）まで使い回す。これがないと、関わりが変わるたびに全部のブロックを見積もり直していた（1 回目 3081 回、2 回目 2030 回）。測る途中のキャッシュ（1 回のレイアウトの間だけのハッシュ表）も試したが、表を引くほうが遅く、見積もりが 11 ms から 18 ms になったので入れていない。

## CSS との違い

| | CSS | ここ |
|---|---|---|
| 覚えた大きさ | `contain-intrinsic-size: auto` を書いたときだけ | 常に |
| 見積もり | ない | `estimate_contents` |
| 画面に近い範囲 | ブラウザによる | ウィンドウの半分ずつ |
| スクロールのずれ | scroll anchoring | 同じ考え方。目印は `auto` の要素だけから選ぶ |

## 選択

`select_all` は、飛ばされた中身の文字（`held`: 飛ばされているせいだけで見えないノード）まで選ぶ。選択の中にある要素は関わりありになるので、全部がレイアウトされ、コピーできる。Chromium と同じく、そのときは全部を整形する。

## 速さ

tokio の CHANGELOG.md（195 KB、約 1000 ブロック）を、幅 1000、高さ 900 のウィンドウの中でスクロールする要素に入れて測った（`anti-webui-markdown` の `tests/view.rs` の `time_a_long_document`、リリースビルド、バッテリー駆動で続けて測った）。

| | 最初の絵まで | 1 ページ下へ（平均 / 最悪） |
|---|---|---|
| 前（全部をレイアウト） | 154 ms | 0.1 ms / 0.3 ms |
| 今 | 71〜76 ms | 1.5 ms / 3 ms |
| Chromium（何もしない） | 68〜108 ms | |
| Chromium（各ブロックに `content-visibility: auto`） | 15〜22 ms | |

- 今の内訳はおよそ、ノードを作る 27、フォント一覧の初期化 15、スタイル 13、見積もり 10、見えているブロックのレイアウト 4（ms）。文書の長さに比例して残るのは、ノード、スタイル、見積もりである。
- 最初の見積もりの高さは 83438 px、全部をレイアウトした高さは 85526 px（2.4 % 短い）。
- Chromium は `<head>` のスクリプトから `offsetHeight` までで、ブラウザの起動とフォントの初期化を含まない。`content-visibility` の方は、スクリプトでレイアウトさせた時点では画面の中の要素も飛ばしている可能性があり、有利に出ている。

手で確かめる用の `examples/bench.md`（214 KB、24 章、図 4 つ）でも、同じ形で Chromium と交互に 4 回ずつ測った（バッテリー駆動）。Chromium のページは、図のないものは前と同じ作り方、図のあるものは `pre.mermaid` を mermaid.js 12.3 で描き、`mermaid.run()` が終わるまでを測った。

| | Chromium | ここ |
|---|---|---|
| 図なし: 最初のレイアウトまで | 96〜141 ms | 71〜94 ms |
| 図あり: 最初のレイアウトまで | 270〜310 ms（mermaid.js の読み込みを含む） | 67〜73 ms |
| 図あり: 図が出そろうまで | 662〜706 ms | 77〜82 ms |
| メモリ（PSS、全プロセス、図ありを表示中） | 493〜496 MB（ヘッドレス、11 プロセス） | 197〜198 MB（ウィンドウと GPU を含む） |

## これから

- 遠いブロックのノードを作らない（見積もりをノードからではなく Markdown のデータから出す）。ノード、スタイル、見積もりの 50 ms 近くが、ほぼ文書の長さによらなくなる。
- 手が空いたフレームに、画面の近くから順に少しずつレイアウトしておく。スクロールの最悪の時間と、見積もりのずれが減る。

## 使う所

- `markdown_view` のいちばん外側のブロック（`auto` と `estimate_contents`）。
- M3 の `text_editor` の「見えている行だけ整形する」も同じ考えで作る。
