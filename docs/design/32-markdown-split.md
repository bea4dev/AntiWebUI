# 32. 左右に分かれた Markdown エディタと、コードブロックの色分け

左にソース、右にプレビューを並べる Markdown エディタ `markdown_split_editor` を作る。あわせて、ビュワーとエディタのコードブロックを tree-sitter で色分けする。土台は `code_editor`（[31](31-code-editor.md)）と `markdown_view`（[28](28-markdown.md)）。比べる相手は VS Code（プレビューを横に開く）と Ghostwriter（Qt WebEngine のプレビュー）。

## 使い方

```rust
let source = signal(std::fs::read_to_string(path)?);
markdown_split_editor(source)       // 編集すると source が変わる
    .theme(MarkdownTheme::default()) // 右側の見た目
    .code_theme(CodeTheme::light())  // 左側と、右側のコードブロックの色
    .on_link(|url| open(url))
    .image(|src| ImageSource::from(dir.join(src)))
    .editor_ref(editor)              // 左側を外から動かす
    .line_numbers(true)
    .split(0.5)                      // 左側の幅の割合（間の線をドラッグで変えられる）
```

例は `cargo run --release -p anti-webui --example markdown_editor --features markdown -- notes.md --split`。

- 左側は `code_editor` で、言語は Markdown、折り返しあり。Ctrl+F の検索と置換、Ctrl+/、括弧の対応、折りたたみはコードエディタのまま使える。
- リストと引用の中の Enter と Tab は `markdown_editor` と同じ（次の項目の記号を足す、空の項目で終える、字下げする）。
- 右側は `markdown_view`。Mermaid の図、表、脚注、絵文字、画像もビュワーと同じ。
- 間の線（幅 5 px）をドラッグすると、左右の幅が変わる。どちらも全体の 15% より狭くはならない。Escape で元に戻る。

## 構成

- `anti-webui-markdown` に `code` feature を足した（既定で有効）。`anti-webui-code` に依存し、`markdown_split_editor` と、コードブロックの色分けを有効にする。
- `anti-webui` の `markdown` feature を有効にすると、tree-sitter と 14 言語の文法も入る。要らなければ `anti-webui-markdown` の `default-features = false` で外せる。
- `code` feature があり、`.highlight(f)` を渡さないとき、ビュワー（`markdown_view`）もライブプレビューのエディタ（`markdown_editor`）も、コードブロックを tree-sitter で色分けする。

## コードブロックの色分け

`anti-webui-code` に `CodeHighlighter` を足した。短いコードを、言語の名前（`rust`、`sh`、`ts` など、コードブロックに書く名前）で色分けする。

```rust
let h = CodeHighlighter::new(CodeTheme::light());
let colors: Vec<(Range<usize>, Rc<Style>)> = h.highlight("rust", "fn main() {}");
```

- 解析は UI スレッドでする。コードブロックは短く、1 つ数十 µs で済む。64 KB（`SNIPPET_LIMIT`）より長いコードは色分けしない（約 10 MB/秒なので、それでも 6 ms ほど）。
- 文法のコンパイル（2〜20 ms）だけはワーカースレッドでする。その言語を初めて見たときは色を付けずに返し、コンパイルを頼む。頼むのは言語ごとに 1 回だけ。
- コンパイルが済むと `ready()` のシグナルが増える。`highlight` は、色を付けられなかったときにこのシグナルを読む。ビュワーはコードブロックの中身を `dyn_view` で作るので、読んだブロックだけが作り直される。ライブプレビューのエディタは、シグナルが増えたら覚えている行を捨てて `redecorate` する。
- 中に別の言語があるもの（HTML の `<script>` と `<style>` など）も色分けする（`code_editor` と同じ injections）。中の言語の文法がまだのときは、結果を覚えずに、もう一度読まれるのを待つ。
- 色分けの結果は、言語とコードのハッシュで 512 個まで覚えておく。
- `markdown_view::highlight(f)` の `f` が返すスタイルは `Rc<Style>` に変えた。スパンごとに `Style` を複製しないためである。

### 直した不具合（作っている途中）

最初は、コンパイルをコードブロックごとに頼んでいた。bench.md（Rust のブロックが 49 個）では、完了の知らせが 49 回来て、そのたびに 49 個のブロックを作り直していた（2,401 回）。言語ごとに 1 回だけ頼むようにした（`code_editor` の injections も同じように直した）。

## 左右のスクロールを合わせる

VS Code のプレビューと同じ考え方で、ブロックの頭の行と、右側でのその高さの間を直線で補う。

- `markdown_view` に、いちばん外側のブロックごとに、ソースでの開始行、右側の箱（`NodeRef`）、上の余白を覚えさせる（クレートの中だけの `Anchors`）。開始行は、文書を解析し直すたびに改行を数えて出す（214 KB で約 0.1 ms。分割エディタのときだけ）。
- 左から右: 左の一番上の行（小数）が入っているブロック i を探し、ブロック i の頭と次のブロックの頭の高さの間を、行の割合で補った高さまで右をスクロールする。最後のブロックの次は、文書の終わりと右側の高さ。
- 右から左: 右のスクロール位置を高さに含むブロックを二分探索で探し、同じように補った行まで左をスクロールする。
- 最初のブロックは、行 0 と高さ 0 から始まるものとして扱う。こうしないと、左が先頭のときに、右は上の余白（24 px）の分だけスクロールしてしまう。
- 長いリストやコードブロックの中でも、行の割合で補う。コードブロックは 1 行の高さが同じなのでずれない。
- 右側の高さはブロックの中で一様ではないので、補った位置は少しずれる。合わせるのは画面の一番上だけで、キャレットの位置ではない。

### どちらがどちらに合わせるか

スクロールしている側（リーダー）に、もう片方を合わせる。

- リーダーが変わるのは、その側でボタンを押したとき、ホイールを回したとき、左でキーを押したときだけ。プログラムからスクロールした側の `on_scrolled` は、リーダーでないので何もしない。これで行ったり来たりにならない。
- 左がリーダーのとき、右の中身の高さが変わったら（`on_resized`）合わせ直す。打鍵でブロックの高さが変わったとき、画面から遠いブロックが初めてレイアウトされて見積もりの高さが本当の高さに変わったときである。遠くへ飛んだときも、これで本当の位置へ寄っていく。

## core に足したもの

- `EditorRef::top_line()`: エディタの箱の一番上にある行を、その行の中のどこかまで含めて小数で返す（`10.5` は 10 行目の真ん中）。行の高さの表（[31](31-code-editor.md) の `Heights`）から求めるので、ノードのない行でも出る。
- `EditorRef::scroll_to_line(line)`: その行が一番上に来るまでスクロールする。
- `NodeRef::offset_in(ancestor)`: 先祖のスクロールする中身の中での位置（論理ピクセル）。`rect()` と違い、先祖がスクロールしても変わらない。
- `KeyboardEvent::is_default_prevented()`。
- `code_editor` に `.value(signal)`（双方向の束縛）、`.on_scrolled(f)`、`.on_key_down(f)`（エディタ自身のキーの前に呼ぶ。`prevent_default` するとエディタは何もしない）。

## プレビューの更新

打鍵のたびに、文書全体を `pulldown-cmark` で解析し直し、変わったブロックだけを作り直す（今までのビュワーと同じ）。

- bench.md（214 KB）で、プレビューだけなら 1 打鍵 1.06 ms（中央値）、最悪 2.2 ms。そのうち約 0.8 ms が全体の解析。
- 変わったブロックの近くだけを解析し直せば 1 ms ほど縮むが、参照リンクの定義や脚注が文書の別の所にあるので、正しく区切るのが難しい。今の速さで 120 Hz の 1 フレームに十分収まるので、後回しにした。
- VS Code はプレビューの更新を 300 ms 待ってから、別のプロセスでする。

## 確かめたこと

- `Ui` を通したテスト（`tests/split.rs` 3 個）
  - ビュワーのコードブロックの色が、ワーカーから届いたあとに付くこと
  - 左の編集が右に出ること
  - 左を 500 行目までスクロールすると、右の一番上近くにその見出しが出ること
  - 右をホイールでスクロールすると、左が付いてくること
- 4 クレート（core、markdown、widgets、code）のテスト 761 個がすべて通る。clippy の警告なし。
- 描いた絵（`ANTIWEBUI_DUMP_FRAME`）: sample.md の左右、Rust、Python、JSON、sh、TypeScript、HTML（中の `<script>` と `<style>` も）、TOML のコードブロックの色。
- 打鍵、ドラッグ、ホイールの手触りは、外から入力を送れないので見ていない。

## 速さ（2026-11-06、電源あり、リリースビルド）

`tests/split.rs` の `time_typing`。ウィンドウは 1600 × 900、倍率 1.8。文書の真ん中の段落で、左で 60 回打った（10 回に 1 回は Enter）。描画まで含めた 1 回の時間。

| 文書 | 最初の絵 | 1 打鍵（中央値） | 最悪 | 匿名メモリ |
|---|---|---|---|---|
| bench.md（214 KB） | 86〜95 ms | 2.19〜2.25 ms | 3.9〜5.2 ms | 64〜66 MB |

コードブロックの色分けで、ビュワー（`time_a_long_document`、bench.md）の最初の絵までの時間は変わらない（計測のぶれの範囲）。文法が届いたあと、49 個のコードブロックを色付きで作り直すフレームが 7〜15 ms ほどかかる。

## ほかのエディタとの比較

bench.md を、ソースとプレビューを横に並べて開いた。時間は起動から表示までで、ウィンドウが開くアニメーションを含む。メモリは起動で増えたプロセス全部の PSS。測り方は [31](31-code-editor.md) と同じで、3 回ずつ交互に測った（2026-11-06、電源あり、出力は NVIDIA）。

| アプリ | 中身 | 表示まで | メモリ |
|---|---|---|---|
| **AntiWebUI（`markdown_split_editor`）** | ネイティブ（wgpu） | 0.88〜0.96 秒 | 287 MB |
| Ghostwriter 26.08.2 | Qt + Qt WebEngine | 1.33〜1.48 秒 | 715〜719 MB |
| VS Code（プレビューを横に） | Electron | 2.59〜3.17 秒 | 1,497〜1,543 MB |

- 参考に、ライブプレビュー（`markdown_editor`、1 画面）は 0.80〜0.93 秒、197〜230 MB だった。
- AntiWebUI のメモリの大半は GPU のドライバで、アプリ自身は約 65 MB（上の表）。
- VS Code は、プレビューを横に開く小さな拡張機能を使った。ワークスペースを信頼するかの確認は切った（確認が出ると拡張機能が動かない）。
- Ghostwriter はパッケージを scratchpad に展開して動かし、設定で `Preview/htmlPreviewOpen` を有効にした。

## 入っていないもの

- 変わったブロックの近くだけを解析し直すこと（上の「プレビューの更新」）。
- 右側を押して左のその行へ飛ぶこと（VS Code はダブルクリックで飛ぶ）。
- キャレットのある行を右側で示すこと。
- 合わせるのは一番上のブロック単位で、リストの項目や表の行の単位ではない。
- 左だけ、右だけの表示への切り替え（`code_editor` か `markdown_view` を単独で使えばよい）。
- 右側の暗い配色（`MarkdownTheme` は GitHub に近い明るい配色だけ）。
