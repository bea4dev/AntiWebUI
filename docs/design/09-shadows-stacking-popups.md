# 09. 影・重なり順・ポップアップ

プルダウンリストのような「他の要素の上に出る UI」を作るための 3 つの機能。

| 機能 | できること | 実装の場所 |
|---|---|---|
| 影 | CSS の `box-shadow`（外側・内側） | core（ペイント）、wgpu（シェーダ） |
| `z_index` | ウィンドウ内での重なり順 | core（レイアウト後のリスト、ペイント、ヒットテスト） |
| `popup` | ウィンドウの外まで出られる別サーフェス | core、wgpu、app、Wayland |

ウィンドウの中で収まるなら `absolute` + `z_index`、収まらない可能性があるなら `popup` を使う。

## 影

### 意味（CSS と同じ）

- ぼかし半径 B はガウスの標準偏差 σ = B / 2 に対応する。
- 外側の影は箱の下には描かない（半透明の背景を透かしても影は見えない）。
- `shadows` の先頭が一番上。描画は逆順に行う。
- `spread` は形を広げ、丸い角の半径も一緒に増やす。角が丸くない箇所は四角のまま。半径は 0 未満にならない。
- `inset` の影はパディングボックスの内側、背景の上・子の下に描く。

### 計算（Evan Wallace の式）

今までの「角丸の距離関数 + erf」は安価だが、角と小さな箱で誤差が大きい。四角い角では真の値 0.25 に対して 0.5 になる。

ShojiWM と同じ、x 方向は解析解、y 方向は 4 点の数値積分で求める方式に変える。σ は 2 次元ガウスなので、行ごとに「その行で角丸矩形が占める幅」を求めて x 方向に積分すればよい。

```
行 t での半幅  c = hx − r + √max(0, r² − min(hy − r − |t|, 0)²)
行 t の被覆   X(x, t) = ½[erf((x + c) / (σ√2)) − erf((x − c) / (σ√2))]
影           = Σ X(px, py − yi) · G(yi) · Δ   （yi は ±3σ を箱で切った範囲の中点 4 つ）
```

調査時の計測（4 倍スーパーサンプリングの FFT ガウスを基準に、10 ケースの箱の外側で測った被覆の最大絶対誤差）:

| 方式 | 最大誤差の範囲 |
|---|---|
| 距離関数 + erf（従来） | 0.048 〜 0.248 |
| Wallace 4 点（採用） | 0.005 〜 0.018 |
| Wallace 8 点 | 0.001 〜 0.006 |

CSS は各ピクセルで 5% 以内を求めている。4 点で足りるので 4 点にする。

Skia は角丸の影を 9 スライスのマスクにしてキャッシュする。こちらはキャッシュを持たず、次の節で描く範囲を減らして毎回計算する。

### 描く範囲を減らす（リム描画）

外側の影は箱の中を塗らないので、箱の内側に矩形の穴を開け、周囲の最大 4 枚の四角形だけを描く。ウィンドウに近い大きさの箱の影でも、フラグメントのコストが縁の分だけになる。

- 穴は「箱を `r × (1 − 1/√2) + 1` だけ内側に縮めた矩形」。角の弧はこの外側にあるので、穴の中は確実に 0 になる。
- `inset` の影も同じ。光る形を `3σ + 1` と角の分だけ縮めた矩形の中は 0 になるので塗らない。
- 影と矩形は**同じパイプライン**で描く。影のあるカードが並ぶと「影 → 箱」が交互に来るので、パイプラインを分けると切り替えが箱の数だけ増える（200 枚で記録が 0.33 ms になった。同じパイプラインなら 0.05 ms）。インスタンスは 8 バイト増えて 136 バイトになる。

### 箱との継ぎ目

箱の中を切り抜くと、角丸のアンチエイリアス部分で「影も箱も半分」になり、明るい線が出る。Blink と同じく、**背景が不透明で角が丸いときは、切り抜きを 1 論理 px 内側に縮める**（はみ出した影は不透明な背景に隠れる）。背景が半透明のときは正確な形で切り抜く。

### 確認

Chrome 155 で同じ箱を描いたスクリーンショットと比べた（800×600、外側・内側・spread・半透明・角ごとの半径の 11 個）。

| 差（256 段階） | ピクセル |
|---|---|
| 2 以下 | 98.54% |
| 4 より大きい | 527。うち箱の縁から 1.5 px より離れたものは 123 で、その差は最大 5 |
| 8 より大きい | 216。すべて箱の縁のアンチエイリアス部分 |
| 13（5%）より大きい | 105。すべて箱の縁のアンチエイリアス部分（最大 44） |

`bench_shadow`（1620×1616、Radeon 880M、1 フレームを全面描画。GPU 時間はぶれが大きいので 4〜5 回の範囲）:

| 場面 | 記録: 前 → 後 | GPU: 前 → 後 |
|---|---|---|
| 影なし | 0.02 → 0.02 ms | 約 0.12 → 0.13〜0.16 ms |
| ウィンドウ大の影 | 0.02 → 0.02 ms | 約 0.24 → 0.17〜0.21 ms |
| 小さな影 200 個 | 0.03 → 0.05 ms | 約 0.18 → 0.29〜0.32 ms |

小さな影がほぼ縁だけでできている場合は穴の効果がなく、精度を上げた分だけ重くなる。

## 重なり順（z_index）

### 規則（CSS 2.1 Appendix E のサブセット）

スタッキングコンテキストの中は次の順で描く。

1. 自身の背景・枠線
2. `z_index` が負の子孫（小さい順）
3. 通常の子孫（木の順）
4. `absolute` で z が未指定のものと `z_index` が 0 以上のもの（z の順、同じなら木の順）
5. 自身のスクロールバー・アウトライン

スタッキングコンテキストを作るもの:

| 条件 | 備考 |
|---|---|
| ルート、ポップアップ | |
| `z_index` が指定されている | CSS と違い `position` は問わない（全ノードが CSS の `relative` / flex item 相当のため） |
| `opacity < 1` | CSS と同じ。リストの途中に透明度を挟まないので、影響を祖先までたどらなくて済む |
| `translate` / `scale` / `rotate` が恒等でない | CSS と同じ。中身がまとめて 1 枚のレイヤーになる（[12](12-transform.md)） |
| `overflow: scroll` | **CSS との違い**。スクロール内容は 1 枚のレイヤーとして丸ごと動くので、外の要素と中の要素を互い違いに重ねられない。はみ出しの有無で振る舞いが変わらないよう、スクロール要素は常にこれにする |

クリップは今まで通り木の親からたどる。`absolute` の包含ブロックが常に親なので、CSS でもすべての祖先のクリップが掛かる場合に当たる。**`z_index` ではクリップから出られない**。出たいときは `popup` を使う。

### リストのキャッシュ（Blink の PaintLayerStackingNode と同じ考え方）

ペイントとヒットテストのたびに子孫を調べないよう、並べ替えたリストを保持する。

- 重ねる対象（`absolute` または `z_index` あり）のノードを文書全体の集合 `stacked` に入れておく。多くの文書で数は少ない。
- 木の構造、`z_index`、`position`、`overflow`、`opacity` が変わったら `stacking_dirty` を立てる。
- 次の更新で位置計算の後に作り直す。各ノードから親をたどって最も近いコンテキストを見つけ、`(z, 文書順)` で並べる。コストは「重ねる対象の数 × 深さ」で、全ノード数によらない。
- 通常の走査では `stacked` のノードを飛ばす。ヒットテストは逆順（正の z → 通常 → 負の z → 自身）。
- リストの要素も `subtree_bounds` でカリングする。

## ポップアップ

### API

```rust
let open = signal(false);
div()
    .child(button("メニュー").on_pointer_down(move |_| open.set(true)))
    .child(show(move || open.get(), move || {
        popup()
            .placement(Placement::BelowStart)
            .on_dismiss(move || open.set(false))
            .child(div().bg(WHITE).rounded(8.0).shadow_lg().child(...))
    }))
```

| 種類 | 用途 | Wayland | 外をクリックすると | 入力 |
|---|---|---|---|---|
| `PopupKind::Menu`（既定） | プルダウン、メニュー | `xdg_popup` + grab | 閉じる | 受ける |
| `PopupKind::Tooltip` | ツールチップ | `xdg_popup` | 閉じない | 素通り |
| `PopupKind::Bubble` | 通知、インスペクタ、補完候補 | `wl_subsurface` | 閉じない | 受ける |

種類と Wayland の役割の対応は Chromium の Ozone/Wayland と同じ（`kMenu` / `kTooltip` → `xdg_popup`、`kBubble` → `wl_subsurface`）。違いが 2 つある。

- **grab**: Chromium は既定では grab せず（`--use-wayland-explicit-grab` で有効）、自分で押下とフォーカス喪失を監視して閉じる。こちらはプロトコルの通り grab して、他のアプリのクリックをコンポジタに任せる。
- **role を付ける前の null バッファの commit**: Chromium は Mutter 向けの回避策としてこれをする。こちらはしていない。Mutter では未確認。

| | `xdg_popup` | `wl_subsurface` |
|---|---|---|
| 画面端での調整 | コンポジタがする | しない（core がウィンドウ内に収める） |
| 表示までの往復 | configure を 1 回待つ | 待たない |
| キーボードフォーカス | grab で移る | 動かない |

### core の構造

ポップアップは**論理的には宣言した場所の子**で、**描画とレイアウトでは別の根**になる（React の portal と同じ）。

| | 木の親（宣言した場所）に従う | 独立している |
|---|---|---|
| 内容 | 寿命（オーナー）、スタイルの継承、イベントのバブリング | レイアウト、位置、クリップ、ペイント、ダメージ |

- ノード種別 `NodeKind::Popup` を追加し、`Document::popups` に登録する。親のレイアウトと描画の走査はこれを飛ばす。
- レイアウトの無効化はここで止まる。ポップアップの中が変わってもウィンドウのレイアウトは走らない。
- スクロールの連鎖もここで止まる。リストの端でウィンドウがスクロールしない。

### 座標

core の中のポインタ座標は**すべてウィンドウ座標**のままにする（ウィンドウの外なら負や範囲外の値）。選択のドラッグやキャプチャのコードはサーフェスを意識しなくて済む。

- ポップアップの中のノードの `abs` は**サーフェス座標**。スクロールレイヤーと同じ「空間」（`Node::space`）の仕組みで、ウィンドウ座標との変換は `space_offset` が行う。動かしても書き換えるものがない。
- プラットフォームは、受け取ったポインタ座標にサーフェスの原点を足してから core に渡す。

### サイズ（論理整数への揃え）

Wayland の位置とサイズは論理 px の整数なので、影を含むサーフェスを次のように決める。`L(v) = ceil(v / s)`、`P(l) = round(l × s)`。

```
内容を計測          → 箱の大きさ w（物理）。影やアウトラインのはみ出し m（物理）
マージン            → 論理 L(m)、箱の位置は P(L(m))
ジオメトリ（箱）     → 論理 L(w)
サーフェス          → 論理 = マージン + L(w) + マージン、バッファ = P(論理)
```

`xdg_surface.set_window_geometry` に箱を渡すので、コンポジタは影を除いた箱を基準に配置する。影の部分はクリックを素通しする（入力領域を箱に限る）。

はみ出しは実際に描くもの（影、アウトライン、テキストの行の範囲）だけで求める。カリング用の `subtree_bounds` は文字のはみ出しを見込んで大きめなので、そのまま使うとサーフェスに透明な余白ができ、コンポジタがその分も合成することになる。

小数スケールでは、整数の論理座標が物理 px の境界に乗るとは限らない。1.8 倍なら論理 11 は 19.8 px で、丸めはコンポジタ次第。アンカーとの間に 1 物理 px 程度のずれが出ることはプロトコル上避けられない。

現在のウィンドウと同じスケールで描き、別スケールの出力にまたがるときはコンポジタの拡縮に任せる。

### 開いて閉じるまで

```
シグナル → show がノードを作る
update   → レイアウト → 大きさが決まる → PlatformRequest::ShowPopup
Wayland  → surface / xdg_popup / grab / commit（バッファなし）
         ← configure（位置と大きさ）→ ack → WindowEvent::PopupConfigured
frame    → Scene を描いて attach → commit
```

- 親（ウィンドウまたは親ポップアップ）に最初のバッファが載るまで、作るのを待つ（プロトコルの要求）。
- 内容やアンカーが変わったら `UpdatePopup` → `xdg_popup.reposition`（v3 以上）。
- `xdg_popup` は上から順に壊す必要があるので、バックエンドは閉じるときに子孫を先に壊す。

閉じる経路は 4 つで、どれも結果は同じ（`on_dismiss` が呼ばれ、以後は作り直されるまで表示されない）。

| 経路 | 例 |
|---|---|
| コンポジタ（`popup_done`） | 他のアプリをクリック |
| 自アプリの別の場所を押す | ウィンドウをクリック（grab 中もイベントは自分に届くので、クライアントが閉じる。プロトコルが求めている）。この押下はウィンドウに渡さない |
| Escape | 既定の動作 |
| 別のメニューを開く | grab できるのは最上位のポップアップの子だけなので、祖先でないメニューを先に閉じる |

押したままのドラッグでの選択（押す → 項目の上で離す）は今回はやらない。

### キーボード

フォーカス（`state.focused`）はポップアップを開いても動かさない。プルダウンなら開いたボタンがキーを受ける。`wl_keyboard` のフォーカスが grab で移っても（IME が掴んでいて移らなくても）core から見れば同じ。

- `wl_keyboard.leave` と `enter` が続くだけなら `Focused(false)` を出さない（自分のサーフェスの間の移動）。
- `text-input` のカーソル矩形はフォーカスのあるサーフェスの座標に直す。

### フレーム

- フレームコールバック、`syncobj`、`opaque_region`、表示用バッファはサーフェスごとに持つ。
- GPU デバイス、レンダラ（グリフアトラス）、acquire タイムラインは共有する。レイヤーのテクスチャは所有するサーフェスの分だけ管理する。
- どのサーフェスにもコールバック待ちがないときに `frame` を実行する（まとめて 1 回）。各サーフェスは自分の差分が空なら commit しないので、リストのホバーでウィンドウは commit しない。
- ポップアップにコールバックが返らないとウィンドウまで止まるので、ポップアップの待ちは 100 ms で打ち切る。
- wgpu Surface へのフォールバックでは、ポップアップも Surface とレンダラを別に持つ（アトラスは共有されない）。

### 残るコスト

- ペイントの無効化はサーフェスごとに分かれていない。ポップアップ内のホバーでウィンドウも描き直す（差分が空なので GPU と commit は発生しない）。コストは `bench_changes` のペイントと差分の分で、2 万行でも 0.1 ms 程度。

## 今回やらないこと

- 押したままのドラッグでのメニュー選択、ツールチップの表示遅延（タイマー API が要る）、サブメニューの自動開閉。
- `xdg_wm_base` v3 未満での移動とサイズ変更（`reposition` が無いので、開いた時の位置とサイズのまま）。
- ウィンドウごとに違うスケールでのポップアップの描画。
- Windows / macOS（どちらもポップアップ用の別ウィンドウで実現できる形にしてある）。
- スクロール内容を独立したサブサーフェスにして合成する最適化（目的が別）。
