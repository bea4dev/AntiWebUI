# 26. PDF

当分の目標は**性能の良い PDF ビュワー**である。ブラウザをオフスクリーンで起動する方式は使わない。

```rust
let viewer = pdf_viewer();
pdf_view("paper.pdf")
    .viewer(viewer)
    .w_full()
    .h_full()
    .on_error(|e| match e {
        PdfError::NeedsPassword => { /* パスワードを聞いて viewer.unlock(..) */ }
        _ => {}
    });

button("拡大").on_click(move |_| viewer.zoom_by(1.25));
button("幅に合わせる").on_click(move |_| viewer.set_zoom(PdfZoom::FitWidth));
text(move || format!("{} / {}", viewer.page() + 1, viewer.page_count()));
```

## 目標

| 項目 | 目標 |
|---|---|
| 速度 | 開いてから画面に出るまで、スクロール、ズームのすべてで Chrome 上の PDF.js 以上 |
| UI スレッド | PDF の読み込みにも描画にも止められない。120 Hz のスクロールを落とさない |
| メモリ | ビュワーの増分を、測ったサンプルで PDF.js のタブより少なくする |
| 依存 | 使わないアプリには何も足さない。`pdf` feature は既定で無効 |

結果は[ビュワーの実測](#ビュワーの実測)にある。

## 土台の選択

**`hayro`（純 Rust、`Apache-2.0 OR MIT`）を使う。** 関連クレート（`hayro-interpret`、`hayro-syntax`、`hayro-jbig2`、`hayro-jpeg2000`、`hayro-cmap`、`vello_cpu`）も同じライセンスである。PDFium は C++ の大きな依存で利点が薄れるので使わず、詰まったときに改めて検討する。

`hayro` の次の点は、ソース（0.9.0）を読んで確かめた。ドキュメントと食い違うものがあるので、ソースを正とする。

| 項目 | 状況 |
|---|---|
| パスワード | `Pdf::new_with_password` がある。`hayro` のドキュメントの「未対応」は古い。Ghostscript で作った RC4 128 bit の文書で確かめた（AES は未確認） |
| ブレンド | `convert_blend_mode` で全種類を渡している。同じくドキュメントの「未対応」は古い可能性が高い。knockout グループは未確認 |
| スレッド | `Pdf` は `Send + Sync`（コンパイルで確認）。`RenderCache` は `Rc` を持つのでワーカーごとに持つ |
| 中断 | できない。下記の[中断](#中断と失敗)を参照 |
| 独自の `Device` | 公開されている。`hayro` の `Renderer` は非公開で、包むことはできない |
| 同梱データ | `embed-fonts`（標準 14 フォント）と `embed-cmaps`（約 250 KB）が既定。CGATS の ICC プロファイルなど個別のライセンスを持つものがあるので、配布前に確認する |

## 構成

| 場所 | 置くもの |
|---|---|
| `anti-webui-pdf`（新規） | `pdf_view`、`PdfViewer`、`hayro` の呼び出し、ワーカーと優先度、フォント解決、文字の抽出、選択と検索 |
| `anti-webui-core` | PDF を知らない汎用の部品だけを足す（下表） |
| `anti-webui` | `pdf` feature と `anti_webui::pdf` の再エクスポート、`examples/pdf.rs` |

動画と違って `core` に `pdf.rs` は置かない。動画は dmabuf の取り込みやフレームの割り振りでレンダラに深く入るが、PDF はできた絵を置くだけで済むからである。バックエンドの trait も `anti-webui-pdf` の内側に置く。

`core` に足すもの:

| 追加 | 理由 |
|---|---|
| `Bitmap` を画素から作る公開 API（ミップなし、乗算済み、不透明の指定あり） | `vello_cpu` の結果を複製せず渡す。`level_count` は今は常に全段なので、段数を持たせる |
| `bitmap_view(signal)`: `Arc<Bitmap>` を箱いっぱいに出すノード | `ImageSource::Pixels` だと乗算、ミップ作成、キャッシュを通るので遅い。`Primitive::Image` はそのまま使う |
| `ui_channel::<T>()`: 別スレッドから送れて、UI スレッドでクロージャが呼ばれる口 | 今はワーカーから UI スレッドを起こす公開 API がない（`set_image_waker` は `core` の中だけ）。送信で起こし、シグナルの更新は UI スレッドで行う（[UI スレッドは 1 本](05-rendering.md)） |
| `set_clipboard(kind, text)` の公開（P3） | 文字のコピーに使う。今は `PlatformRequest::SetClipboard` が `core` の中だけ |
| `NodeRef::scroll_to_after_layout` | ズームではページの大きさとスクロール位置を同じフレームで変える。今の `scroll_to` は古い大きさで切り詰められる |

見えている部分だけ作る仕組みは、`virtual_list` が行の高さ一定を前提にしているので使わず、ページの累積位置の表と二分探索で `anti-webui-pdf` の中に持つ。

## 流れ

```
UI スレッド                          ワーカー
pdf_view("a.pdf") を作る ──────────→ ファイルを読む、Pdf::new
                                     全ページの大きさを取る
        ←── ページ数、大きさ ──────
ページの位置の表を作り、スクロール範囲が決まる
見えているページを要求 ─────────────→ 優先度順に描く（hayro::render_into）
        ←── Bitmap ─────────────
bitmap_view を更新、次のフレームで GPU へ
```

メモリの複製を避けるため、ワーカーの画素はそのまま `Bitmap` にする。GPU に転送したら CPU 側を手放す（画像と同じ）。

### 大きさ

- 100% は CSS と同じ `1 pt = 96 / 72 論理 px` である。拡大率 1.8 なら `1 pt = 2.4 物理 px`。
- ページの箱は物理 px の整数に丸め、絵はその大きさちょうどに描く。`x`、`y` の倍率を `箱の px / ページの pt` にするので、絵と画面の画素が 1 対 1 になり、文字がにじまない。
- 位置は `Length::Device` で持つ。`f32` の精度から、なめらかに動く高さはおよそ 1600 万物理 px までである（[21](21-widgets.md)）。A4 を幅合わせで約 7900 ページ分にあたる。これを超える文書のページ単位表示は後回しにする。

## 描画

### 全体の絵と部分の絵

1 ページにつき最大 2 枚の絵を持つ。

| 絵 | 範囲 | 倍率 |
|---|---|---|
| 全体 | ページ全体 | 今の倍率。ただし上限（1600 万 px かつテクスチャの最大サイズ以下）まで |
| 部分 | 見えている範囲と周囲の余白 | 今の倍率ちょうど。全体の絵が上限で足りないときだけ作る |

全体の絵は上限ぎりぎりのページで倍率が変わると丸めで 1 px ほどずれる。それだけでは描き直さない（2 px まで同じものとして扱う）。

- 800% の A4 は約 1.85 億 px あり、全体を絵にできない。全体の絵を引き伸ばして下に敷き、見えている所だけ部分の絵で覆う。
- 余白は箱の大きさの 0.5 倍ずつ上下左右に取り、面積は 4 倍になる（PDF.js は 1 倍ずつで 9 倍）。絵は 1600 万 px までなので、箱が 400 万 px を超える画面では余白を減らす（4K で約 0.2 倍）。
- 見えている範囲に余白の半分を足した範囲が絵からはみ出したら、次の部分を要求する。使い切る前に頼むので、描いている間に余白を使う。
- 要求中の部分はページごとに覚えておき、そのままで足りる間はスクロールしても変えない。変えると、始まっていない仕事を毎フレーム捨てることになる。
- 倍率が変わっている間、古い部分の絵はページ上の同じ場所に引き伸ばして残す。全体の絵だけで足りる倍率に戻ったら、その場で捨てる。
- 描き終わった部分は、倍率が古いもの、または今あるものより見えている範囲を含まないものなら使わない。
- 格子状のタイルにしない理由は、`hayro` がタイルごとにページ全体を解釈し直すからである。大判地図では解釈だけで 262 ms かかるので、タイルの数だけ時間が伸びる。タイルが効くのは、描画命令を記録して使い回す[段階 3](#段階-3-独自の-device) からである。

### ズーム

1. Ctrl + ホイールやボタンで倍率を変えると、そのフレームでレイアウトを変える。ポインタの下の点が動かないようにスクロール位置も直す。
2. 今ある絵を引き伸ばして表示する（画像の `want` と同じ考え方）。
3. 新しい倍率の描画を要求する。**待ち時間を置かず**、古い要求は開始前に捨てる。軽いページは連続ズームに追従し、重いページは最後の倍率だけが描かれる。

絵にはミップを持たせないので、縮小中の数フレームは粗くなる。VRAM を 33% 増やすほどの価値はないと考えた。目で見て気になるなら考え直す。

### 優先度

上から順に、空いたワーカーが取る。古い倍率の要求は開始前に捨てる。

1. 見えているページの全体の絵（画面に占める面積が大きい順）
2. 見えているページの部分の絵
3. スクロールする方向の次の 2 ページ、反対方向の 1 ページ
4. 文字の抽出（要求されたページだけ）

PDF.js 6.5 の `getHighestPriority` も、見えているページ、部分の絵、抜けているページ、先読みの順である。先読みは次の 1 ページ（条件によりもう 1 ページ）。

### ワーカー

全ページを 1 回描く時間（論文 15 本、計 146 ページ、幅 1429 px）:

| ワーカー | 時間 | メモリのピーク |
|---|---|---|
| 1 | 7857 ms | 181 MiB |
| 2 | 4350 ms（1.8 倍速） | 314 MiB |
| 4 | 3484 ms（2.3 倍速） | 384 MiB |
| 8 | 3331 ms（2.4 倍速） | 450 MiB |

既定は **2 本**にする。1 ページの描画が数 ms なので、ほとんどの場面では 2 本でも余り、4 本にしても速さのわりにメモリが増える。`pdf_view(..).workers(n)` で変えられる。設定を `core` に置くと PDF を知ることになるので、`Settings` には入れない。一方、`vello_cpu` のマルチスレッドは 8 スレッドでも大判地図が 517 ms から 436 ms になる程度だったので、使わない。

仕事がなくなって 10 秒でワーカーは終わり、キャッシュも捨てる（画像のワーカーと同じ）。

### メモリ

- 絵の合計の上限は 256 MiB とする（`pdf_view(..).cache_bytes(n)`）。幅 1429 px の A4 は 1 枚 11.5 MB なので、約 22 ページである。
- 見えているページの絵と部分の絵は上限を超えても残す。
- 先読みは上限に収まる分だけ頼む。頼んだものを捨てると、また頼むことになって永遠に描き続けるからである（P1 にはこの問題があった）。
- 超えたら、今の計画にないページを遠い順に捨て、次に見えていないページの古い倍率の絵を捨てる。
- 部分の絵は見えなくなったらすぐ捨てる。
- PDF.js は 10 ページ（画面の 2 倍 + 1 ページが多ければそちら）を保持する。絵 1 枚の上限は 2^25 px（約 3355 万）である。

### フォント

埋め込みのないフォントは `InterpreterSettings::font_resolver` で解決する。これを省くと日本語が消える（実際に `IPSJ-OS26171014` の図の説明文と、論文の © が消えた）。

| 要求 | 解決 |
|---|---|
| Adobe-Japan1 / GB1 / CNS1 / Korea1 | `is_serif` と言語からシステムのフォントを選ぶ |
| 標準 14 フォント | システムの Liberation / Arimo など（[04](04-text.md) の `STAND_INS` と同じ考え方）、無ければ同梱のもの |
| それ以外 | `pick_standard_font` |

- 呼ばれるのはワーカーなので、UI スレッドの `TextSystem` には触れない。`anti-webui-pdf` で `fontique` の `Collection` を別に持ち、最初に要求されたときに読む。
- フォントは mmap で渡し、使うものだけを開く。全部読むと論文で 44 MiB 増えた（176 MiB から 220 MiB）。

### 中断と失敗

`hayro` は描画を途中で止められない。これは[上の方針](#優先度)の前提になる。

| 状況 | 対応 |
|---|---|
| 要求が古くなった | 開始前なら捨てる |
| 描画中に古くなった | 終わるのを待って結果を捨てる。ワーカーがすべて古い仕事で 200 ms 以上ふさがっているときだけ、1 本足して続ける（合計 8 本まで）。増やした分は 1 つ描くと消える |
| `hayro` のパニック | ジョブごとに `catch_unwind` で受けて、そのワーカーのキャッシュを捨てる。全体の絵ならページに「描けない」と出して `on_page_error(page)` を呼び、部分の絵ならそのページの部分を頼むのをやめて全体の絵のままにする。どちらも描き直さない |
| 大きすぎるページ | 絵の px の上限で防ぐ。画像デコードのメモリまでは防げない |
| GPU のテクスチャより大きい絵 | ウィンドウのデバイスの上限はアダプタのまま（普通は 16384）で、8192 までの絵は入る。それより小さい GL のアダプタでは、画素を間引いて出す |

強制終了は使わない。`pthread_cancel` などは、アロケータのロックを握ったまま止まるとアプリ全体を固める。信頼できないファイルは、別プロセスで開いて kill するしかない（[後回し](#後回しにするもの)）。

## 文字

PDF.js は透明な DOM を重ねて選択を実現しているが、ここでは持たない。

- 抽出は `Device` を実装した `TextDevice` で行う。`draw_glyph_run` から Unicode、変形、送り幅を集め、他の描画命令は捨てる。解釈だけなので、論文で 1 ページ約 0.5 ms である。
- ページにポインタが入ったとき、または検索で必要になったときに、優先度 4 でページごとに抽出する。読まないページの分のメモリは使わない。
- 選択はビュワーが自分で持つ。始点と終点を（ページ、グリフ）で持ち、複数ページにまたがれる。色はページの上に重ねる半透明の箱で塗る。**[04](04-text.md) のドキュメント全体の選択とは別物**である。
- 順序は内容ストリームの順にする。二段組の論文でも、たいていはこれで読む順になる。
- 改行と空白は、グリフの間隔とベースラインの変化から推定する。日本語の行末には空白を入れない。
- Ctrl + C でコピーし、Wayland のプライマリ選択にも入れる。
- 検索は全ページを順に抽出して、見つかった数をシグナルで増やしていく。大文字小文字と全角半角を同一視し、行をまたいだ語も見つける。

## リンクと目次

`hayro-syntax` はこれらを公開していないが、`page.raw()` と `Pdf::xref()` で辞書を読める。

- `/Link` の注釈の `/URI` と `/Dest`。カーソルを変え、クリックで移動するか `on_link` を呼ぶ。外部 URL をその場で開くことはしない。
- カタログの `/Outlines` を `viewer.outline()` で返す。目次の見た目はアプリに任せる。

## 段階 3: 独自の `Device`

描画命令を一度だけ記録し、空間索引を付けて、見えている分だけを描く。次の問題を解決できる。

| 問題 | 実測 |
|---|---|
| 巨大画像のページが遅い | `IPSJ-OS26171004` の 3 ページ目が 906 ms（PDFium 151 ms）。1 枚約 4000×2000 px のマスク付き画像が 3 枚 |
| 部分の絵のたびに解釈し直す | 大判地図の 800% で 376 ms（解釈だけで 262 ms） |
| 800% で PDFium に負けるページがある | ニューヨークの路線図 78 ms（PDFium 37 ms） |
| 描画の中断 | `Device` の呼び出しごとにフラグを確認できる（何もしなくなる、または `resume_unwind`） |

ただし最初は作らない。**今の実測では PDF.js より十分速いので、計測で必要と分かってから**にする。`Device` は描画命令を CPU の絵に描くところまでにし、GPU に直接描くかどうかは改めて判断する。

## 検証

計測の道具は `src/anti-webui-pdf/tools/` に置く。下の「`hayro` 単体の実測」の道具と生データは `/tmp` にあり、再起動で消えた。サンプルの PDF はライセンスの都合で置かず、`compare.py --fetch` で取得する。

- **速さ:** `anti-webui-app` の `examples/bench_pdf.rs` で、開いてから最初のページが GPU に描かれるまでと、一定速度のスクロール中のフレーム時間と白いままの量を測る。`tools/compare.py` が同じ操作を Chromium の PDF.js のビュワー部品（`tools/pdfjs_page.html`）で測って並べる。`--zoom 800` で 800% の表示も比べる。
- **壊れた文書:** `src/anti-webui-pdf/examples/broken.rs` が、ランダムに壊した文書を描いて、パニックと遅いページを報告する。
- **正しさ:** PDFium（`pypdfium2`、開発時のみ）の画素と比べる。24 px 角のブロックの差で内容の欠落を検出する。文字のアンチエイリアスの差はこれで無視できる。
- **回帰テスト:** 小さな PDF を生成して描画し、位置と色を確かめる。優先度とメモリの上限は、描画を差し替えられるバックエンドで単体テストする。

| 論文 `IPSJ-OS26171004`（巨大画像） | 80 / 286 | 99.4% / 9.5% | 84.5% / 1.8% | 657 / 940 |
| Vulkan のスライド | 69 / 204 | 99.4% / 9.5% | 99.2% / 3.0% | 568 / 858 |
| スキャン書籍 | 150 / 356 | 99.4% / 9.5% | 79.4% / 3.3% | 712 / 1030 |
| ロンドン地下鉄路線図 | 106 / 492 | 99.4% / 9.3% | 99.1% / 4.5% | 444 / 1048 |
| USGS の大判地図 | 407 / 3574 | 99.4% / 9.8% | 14.8% / 2.6% | 656 / 1770 |

- **くっきりした割合**は、窓のうち画素が 1 対 1 の絵で覆われている割合の時間平均である。ページの間の隙間があるので 100% にはならない。両方とも実際に表示されている絵で数えた。幅に合わせた表示では PDF.js の全体の絵が 1 対 1 に近いのに割合には入らないので、この欄は 800% でだけ比べる。
- PDF.js は止まらずスクロールし続けると、部分の絵を取り消して描き直すのを繰り返し、完成しないことが多い。その間は小さな全体の絵（tracemonkey で 528×683 px）を引き伸ばして見せる。低い割合はこのためで、スクロールを止めれば 1 秒以内にくっきりする。AntiWebUI は全体の絵も最大 1600 万 px あるので、大判地図で部分が間に合わないときの粗さも小さい。
- 「出るまで」は AntiWebUI が GPU の完了まで（読み戻し約 10 ms を含む）、PDF.js が `pagerendered` の後に 2 回の `requestAnimationFrame` まで（テキストレイヤーを含む）である。開く時間は AntiWebUI が 15〜27 ms、PDF.js が 38〜138 ms。
- 白いままの量は AntiWebUI が絵のない行、PDF.js が描画が終わっていない見えているページである。定義が少し違うので、桁の差として読む。
- フレームの CPU 時間は AntiWebUI の p95 が幅合わせで 0.1〜0.6 ms、800% で 0.5〜3.2 ms である。PDF.js の値は `requestAnimationFrame` の間隔で（16.7 ms 以上）、同じものではない。
- メモリは AntiWebUI が `VmHWM` で GPU ドライバのマップを含み、PDF.js はブラウザのプロセス全体の PSS である。
- 最初に測った表（電池駆動）のメモリは 335〜808 MiB と大きかった。これは計測の間違いで、`bench_pdf` だけ実際のアプリと違って GPU に送った後も画素を持っていた。
- 実際のウィンドウでは、最初のフレームまで約 1.08 秒、そこから絵が出るまで約 0.1 秒だった。前者は SVG のデモでも 1.12 秒で、PDF によるものではない。フレームを書き出す設定で測ったので、その分を含む。

### 新しい絵が届いたフレーム

P1 の時点では、新しい絵が届いたフレームは毎回 15〜17 ms かかると考え、転送を分ける予定だった。**これは誤りだった。** 分けて測ると次のとおりで、転送は分けないことにした。

| 場面 | 時間（Radeon 880M） |
|---|---|
| 新しい絵 30 MB、普段 | 約 2 ms（`create_texture` 0.01 ms、`write_texture` 1〜2 ms） |
| 部分の絵 45〜60 MB、普段 | 約 2.5 ms |
| メモリの塊を増やすとき | `create_texture` が 10〜13 ms。1 回の起動で 1〜3 回 |

分けると絵が出るのが数フレーム遅れるだけで、8.3 ms の枠に対して得るものがない。残るのは塊を増やすときの 1 フレームで、大きな絵の転送と重なると 15〜20 ms になる。

`wgpu` の `MemoryHints` で塊を小さくすることも試したが、既定（GPU 側 128〜256 MiB、一時領域 64〜128 MiB）のままにした。

| 設定 | 結果 |
|---|---|
| 128 MiB 固定（一時領域 64 MiB） | 増やすときは 7 ms になるが、45 MB の転送で一時領域が足りず、以後ずっと 7.5 ms かかるようになった |
| 64 MiB 以下 | 53 MB の絵で毎回 10 ms 以上 |
| 192 MiB 固定 | 増やすときが 9 ms。差が小さく、8.3 ms にも収まらない |

減らすなら、別のスレッドでテクスチャを作るしかない。それには絵が間に合わないフレームの扱いが `core` まで必要になるので、スクロールでカクつくと報告されてから考える。

### 壊れた PDF

`examples/broken.rs` で、5 文書から切り詰め、バイトの書き換え、ゼロ埋めで 300 個の壊れた文書を作って描いた。開けなかったのが 87 個、開けた 213 個から 602 ページを描いて、パニックは 0 回、1 ページの最悪は 393 ms だった。実物でパニックを起こせていないので、失敗の画面は `hayro` を差し替えた単体テストで確かめている。

## `hayro` 単体の実測

2026-11-05、Ryzen AI 9 365、電池駆動。`hayro` 0.9.0、PDF.js 6.5.438（Chromium 154、ビュワーの既定の設定）、PDFium は `pypdfium2` の配布ビルド（AGG。Chrome の Skia 版は外から測れなかった）、MuPDF 1.28.6。ページごとに 2 回の良い方を取り、902 回の実行でパニックもタイムアウトもなかった。2 割程度の差は誤差と考える。

`hayro` は描画だけの時間で GPU への転送を含まず、PDF.js はテキストレイヤーの構築を含まない。Chrome の組み込みの PDF ビュワーは測れていない。

幅 1429 px で 1 ページ描く時間（中央値、ms）:

| 文書 | `hayro` | PDFium | MuPDF | PDF.js |
|---|---|---|---|---|
| 情報処理学会の論文 15 本 | 7.9 | 12.8 | 10.1 | 56.3 |
| tracemonkey（論文） | 6.4 | 5.3 | 4.0 | 32.6 |
| PDF 32000 仕様書（756 ページ） | 2.7 | 3.8 | 2.7 | 16.9 |
| Vulkan のスライド | 3.8 | 7.8 | 11.7 | 29.0 |
| スキャン書籍（JPX + JBIG2） | 87.7 | 108.0 | 169.4 | 128.0 |
| ロンドン地下鉄路線図 | 23.3 | 25.8 | 62.8 | 188.7 |
| ニューヨーク地下鉄路線図 | 44.9 | 60.9 | 114.0 | 241.5 |
| USGS の大判地図 | 516.9 | 941.9 | 1536.8 | 1654.0 |

- `hayro` は 284 ページのすべてで PDF.js より速かった（比の中央値 0.17）。PDFium には 86% のページで勝ち、合計時間はほぼ同じ（9404 ms と 9438 ms）である。
- 開く時間は `hayro` が 0.1〜16 ms、PDF.js はワーカーの起動を含めて 61〜138 ms である。
- 800%（2560×1600 の範囲）の中央値は、論文 9.6 ms、大判地図 376 ms、ニューヨークの路線図 78 ms である。第三者の報告にある最悪 22 秒、5 GB は、今回のサンプルでは再現しなかった。そのファイルは試せていない。
- メモリのピークは `hayro` が 28〜180 MiB、PDFium が 37〜206 MiB、MuPDF が 79〜486 MiB、Chromium はブラウザ全体で 529〜1360 MiB である（PDF.js だけの値ではない）。

解釈だけの時間（`DummyDevice`）は、論文で 0.5 ms（全体 7.9 ms）、大判地図で 262 ms（全体 517 ms）である。普通の文書では解釈は支配的ではなく、描画と画像の処理が大半を占める。

描画の正しさは、文書ごとに最大 5 ページを PDFium と比べた。フォント解決を入れた後は内容の欠落を検出せず、差は他のライブラリ同士と同程度だった。粗いブロック単位の検査で、目視は一部である。透明効果を特に多用する PDF と CAD 図面は試せていない。
