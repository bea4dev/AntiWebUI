# 31. コードエディタ（シンタックスハイライト）

最軽量級、最速級のコードエディタを作る。比べる相手は VS Code、Zed、Sublime Text、Kate、gnome-text-editor、Chromium の CodeMirror 6（比べるためだけに使う）。土台は M3 の `text_editor`（[28](28-markdown.md)）。後で作る Markdown のソースモードもこの上に載せる。

## 調べたこと

### 今の `text_editor` の限界（2026-11-06、電源あり、リリースビルド）

素の `text_editor` に sqlite3.c（9.3 MB、262,899 行）の先頭から入れて測った。

| 行数 | 作る | メモリ（RssAnon） | 1 打鍵 |
|---|---|---|---|
| 5,000 | 46 ms | 88 MB | 0.54 ms |
| 50,000 | 274 ms | 810 MB | 12 ms |
| 262,899 | 1.4 秒 | 4.2 GB | 84 ms |

- ノード 1 つが 7,560 バイトあった。うち 5,360 バイトが `NodeStyle` で、hover、focus、active、dragging、drag_over の `Option<Style>`（1 つ 888 バイト）を使わなくても持っていたため。1 行はノード 2 つなので約 15 KB。
- 全部の行をノードにしていた。`content-visibility` で整形は飛ばせても、ノードを作る時間とメモリは行数に比例する。
- 1 打鍵で文書全体を何度も写していた（文字列の複製 3 回、`Signal<String>` との比較、`decorate` が全行を返す、行の比較が全行）。

VS Code、CodeMirror 6、Zed はどれも見えている行（と少しの余白）しか作らない。

- `tree-sitter-highlight` は呼ぶたびに全部を解析し直すので、エディタには使わない。
- Helix の `tree-house` は差分の解析と埋め込みに対応しているが、MPL-2.0 で `ropey` に縛られ、API もまだ変わる。使わない。
- Zed は、解析し直すのを UI スレッドで 1 ms だけ試し、終わらなければ別スレッドに回す。その間は古い木で描く。色を取り出すのは見えている範囲だけ。
- VS Code は TextMate の文法をワーカーで 20 ms ずつ処理し、20 MB か 30 万行を超えるファイルは色分けしない。CodeMirror 6 は変更の直後に 20 ms、あとは手が空いたときに解析し、描くのは見えている範囲に 1,000 px を足した分。

tree-sitter を直接使い、薄い層を自分で書く。

## core の土台

### ノードを軽く

`NodeStyle` の状態ごとのスタイルを `Option<Box<Style>>` にした。ノードは 7,560 から 3,160 バイトになった。

### 見えている行だけ作る

`text_editor` の行のうち、ノードを作るのは見えている範囲と上下の余裕（ウィンドウの高さ 1 枚分ずつ）の行と、キャレットのある行だけにする。それ以外の行は、続いている分を 1 つの隙間の箱（高さだけの `div`、`Length::Device`）にまとめる。

```
host
├─ 隙間（行 0〜1199 の高さの合計）
├─ 行 1200
├─ …
├─ 行 1350
├─ 隙間（行 1351〜1999）
├─ 行 2000（キャレット）
└─ 隙間（行 2001〜）
```

- 高さは行ごと（正確には、その行から始まる行の箱ごと）に持つ。レイアウトした行は測った高さ（上下のマージンを含む）、まだの行は見積もり。行の番号で持つので、何行かを 1 つにする所（`Row::Block`）が変わっても作り直さない。編集では変わった行の範囲だけを差し替え、行数が変わらなければ測った高さをそのまま残す（次に測るまでの仮の値として）。
- 各行の上端は、高さの累積の表で持つ。変わった行から後ろだけを足し直す。行の箱が 1 行ずつで折り返さない（コード）ときは、測った高さの表をそのまま足すだけの速い道を通る。測った高さが数えていた見積もりと同じなら、足し直さない。
- 見積もりは CodeMirror 6 の `HeightOracle` と同じ考え方。行の高さと 1 文字の幅を、レイアウトした素の 1 行（スタイルのない行）から覚えておき、折り返すときは「文字数 × 文字の幅 ÷ 幅」の行数、折り返さないときは 1 行とする。何も測っていないうちは文字の大きさの 1.3 倍。
- レイアウトのあとで、見えている範囲（`visible_part`）から欲しい行の範囲を求める。今の範囲が見えている範囲と余裕の半分を覆っていなければ、範囲を作り直して、同じ `update` の中でレイアウトし直す。最初の絵に空の所は出ない。
- 範囲を作り直すときは、残る行のうち見えている最初の行を目印にして、スクロールが跳ねないようにする（[29](29-content-visibility.md) の scroll anchoring をそのまま使う）。画面の外へ出る行は測った高さで隙間に入るので、何も動かない。
- 行の箱の `content-visibility: auto` はやめる。作った行は全部レイアウトする。測った高さが要るからである。
- キャレットのある行は、遠くても作る（IME の位置、`scroll_into_view`）。
- 上下、Page Up/Down は、行き先が作った行の中にある。余裕が 1 画面分あるので、Page Up/Down の行き先も作った行に入る。
- 隙間に当たったとき（ふつうは起きない）は、その行の頭にする。

### 1 打鍵で文書全体を写さない

- 文字列と行頭の表を `Rc` で持ち、`decorate` に渡すときは `Rc` を複製する（O(1)）。編集は `Rc::make_mut` で、渡した分が戻っていれば写さない。外で `Rc` を持ったまま編集すると全体を写すことになるので、`code_editor` のキーの処理は、文字列を借りている間に何をするかを決め、手放してから編集する（sqlite3.c の Enter が 2.0 ms から 0.8 ms になった）。
- 前の文字列の写し（`shown`）をやめ、作った行が自分の行の文字列を持つ。
- 行の高さの表は、編集で変わった行の範囲だけを差し替える。
- 文字列は `String` のまま。9 MB の文字列の途中に 1 文字入れると、後ろを 1 回動かす（下の「確かめたこと」）。tree-sitter、検索、`pulldown-cmark` が続いた `&str` を読めるのは大きい。rope は、これが足りなくなったら考える。
- `value(Signal<String>)` は、変わるたびに文字列を写して比べる。大きなファイルでは `on_change`（`&str` を渡す）か、`EditorRef::text()` で必要なときだけ取る。`code_editor` は `value` を使わない。

### 行ごとの装飾（`decorate_lines`）

`decorate` は全行の `Row` を返す（Markdown 用、今のまま）。コードエディタには、作る行の分だけを聞く形を足す。

```rust
text_editor()
    .decorate_lines(|cx: &DecorateContext, lines: Range<usize>| -> Vec<Rc<LineLook>>)
    .blocks(|cx: &DecorateContext| -> Vec<(usize, Row)>)   // 何行かを 1 つにする所（折りたたみ）。最初の行と Row::Block
    .on_edit(|edit: &TextEdit| ...)                         // 変わるたびに、どこがどう変わったか
```

- `decorate_lines` は、作る行が変わるとき、文字列か選択が変わるとき、`EditorRef::redecorate()` を呼んだときに、作る行の分だけ呼ばれる。変わらない行には同じ `Rc` を返す。
- `blocks` は文字列か選択が変わるたびに呼ばれ、まばらな一覧を返す。行と行番号の対応は、この一覧を二分探索して求める。
- `on_edit` には、変わった位置（バイトと、行と列）を、`decorate` より先に 1 つずつ渡す。tree-sitter の `InputEdit` に必要なものが揃う。
- `text_editor().text(s)` で、シグナルなしに始めの文字列を渡せる。`EditorRef::replace_and_select` は、置き換えと選択を 1 回の更新（取り消しも 1 段）でする。

装飾が変わっても箱のスタイルだけのときは、文字を整形し直さない。

### 行番号（`gutter`）

```rust
text_editor().gutter(Style)   // 各行の左に行番号。Style は幅、色、余白
```

- 行の箱の左に余白（行番号の幅）を取り、行番号の箱を絶対配置で文字の後ろに置く（文字より上に描かれる）。行番号が変わる（上に行が増える）ときは、番号の文字だけを差し替える。何行かを 1 つにした行（折りたたんだ所）には番号を付けない。
- 幅は「桁数 × 数字の幅 + 左右の余白」。数字の幅は、最初にレイアウトした番号から測る（それまでは文字の大きさの 0.6 倍）。
- 横にスクロールしても行番号は動かない。CSS の `position: sticky; left: 0` の代わりに、行番号の箱の `left` をスクロールの量だけずらす（横にスクロールしたときだけ、作った行の分の位置を決め直す）。背景を塗っておくので、下を流れる文字は隠れる。
- 今の行の番号は `Gutter::current` のスタイル。

```rust
Gutter { style, current, digits: 3, padding: (12.0, 16.0) }
```

## `anti-webui-code`

```rust
let doc = editor_ref();
code_editor(source)                 // 最初の文字列
    .language(Language::Rust)       // または Language::from_path(path)
    .theme(CodeTheme::dark())
    .on_change(|text| ...)
    .editor_ref(doc)
```

### 色分けの流れ

1. 開いたとき: 文法の規則のコンパイル（Rust で約 10〜20 ms、言語ごとにプロセスで 1 回）と最初の解析を、解析用のスレッドでする。最初の絵は色なしで出し、色は届いてから付ける（2,000 行の Rust で約 10 ms 後）。
2. 打鍵: `on_edit` で木に `edit` を伝える（位置がずれるだけなので、古い色が文字についていく）。UI スレッドで最大 1 ms 解析し直し、終わらなければ解析用のスレッドに文字列の写しと木を渡す。前の打鍵で間に合わなかった文書は、しばらく UI スレッドで試さない。
3. 解析が終わったら（`ui_channel`）、その間の編集を木に伝え、作っている行の色を作り直す（`redecorate`）。
4. 色を取り出すのは作る行の範囲だけ（`QueryCursor::set_byte_range`）。捕捉は外側から内側へ重ね、同じ範囲のものは「長く書かれたパターン（条件の多い、具体的なもの）が勝ち、同じ長さなら先のもの」とする。tree-sitter 自身のハイライタは先のパターンを勝たせるが、それでは Rust のメソッド呼び出し（`a.lock()`）が、規則の先頭にある `(field_identifier) @property` に負けてフィールドの色になる。VS Code と同じく関数の色にしたいので、具体的なものを勝たせた。
5. 捕捉の名前（`keyword`、`function.method` など）からスタイルへ。見つからなければ `.` の前（`function`）を使う。Zed、Helix、Neovim と同じ。

解析用のスレッドは 1 本で、使う側からは見えない（[UI スレッドは 1 本](05-rendering.md)）。結果は `ui_channel` で UI スレッドに戻る。

行ごとの見た目（`LineLook`）は、行の番号ごとに「色の区間、検索、括弧、今の行、長すぎる行、折りたたみ」の鍵と一緒に覚えておき、鍵が同じなら同じ `Rc` を返す。検索で見つかった所や括弧の背景は、色のスタイルに背景を足したスタイル（組み合わせごとに 1 つ作って使い回す）にする。

### 埋め込み（Markdown のコードブロック、HTML の `<script>`）

`injections.scm` を作る行の範囲で走らせ、見つかった部分を、その言語で `set_included_ranges` を使って解析する。部分の木は（言語、位置、中身のハッシュ）で覚えておき、変わらなければ使い回す。Markdown の行内（`tree-sitter-md` の inline 文法）もこれで色を付ける。

### 言語

1 言語ずつ Cargo の feature にする。既定は次のとおり。

| feature | 文法の crate | 大きさの目安 |
|---|---|---|
| `rust` | tree-sitter-rust | 1.1 MB |
| `c`、`cpp` | tree-sitter-c、tree-sitter-cpp | 0.6 MB、3.5 MB |
| `python` | tree-sitter-python | 0.5 MB |
| `javascript`、`typescript`（TSX を含む） | tree-sitter-javascript、tree-sitter-typescript | 0.4 MB、2.9 MB |
| `json`、`toml`、`yaml` | tree-sitter-json、tree-sitter-toml-ng、tree-sitter-yaml | 小さい |
| `markdown` | tree-sitter-md（block と inline） | |
| `html`、`css` | tree-sitter-html、tree-sitter-css | |
| `bash`、`go` | tree-sitter-bash、tree-sitter-go | |

色分けの規則（`highlights.scm`）は各 crate に入っているものを使う。

### 機能（最初の版）

| 機能 | 操作 |
|---|---|
| 色分け | 上のとおり |
| 行番号、今の行 | 今の行は背景と行番号の色 |
| 括弧の対応 | キャレットの隣の括弧と、その相手に薄い背景。相手は構文木で探す（文字列やコメントの中の括弧に惑わされない） |
| 自動の字下げ | Enter で今の行の字下げを引き継ぐ。`{`、`(`、`[`、`:`（Python）で終わる行なら 1 段深くする。行頭で `}` などを打つと 1 段戻す |
| Tab | 選択した行の字下げ（Shift+Tab で戻す）。字下げの単位は言語ごと（既定は空白 4 つ、JavaScript、TypeScript、JSON、YAML、HTML、CSS、Markdown は 2 つ、Go はタブ）。字下げの中の Backspace は 1 段ぶん戻す |
| コメントの切り替え | Ctrl+/ で選択した行の行コメント |
| 検索と置換 | Ctrl+F、Ctrl+H で上に出る欄。選択した 1 行の文字が入る。打つたびに次の一致を選ぶ。Enter（F3）で次、Shift+Enter（Shift+F3）で前、Esc で閉じる。大文字と小文字の区別（Aa）、正規表現（.*、`regex`、置換で `$1`）。「All」は 1 段の取り消しで全部置き換える。一致は 10 万個まで |
| 折りたたみ | 字下げで決める（その行より深く字下げされた続きの行。間の空行を含む）。言語の文法を見ない、VS Code の既定と同じ方法。Ctrl+Shift+[ でキャレットの行（またはそれを含むいちばん近い行）をたたみ、Ctrl+Shift+] で開く。たたんだ行は残し、その末尾に「⋯」（押すと開く）を出す。隠す行は高さ 0 の `Row::Block` にする。隠した行に選択が入ると開く。前で行が増減すると一緒に動き、中が編集されると開く |
| 長すぎる行 | 1 万バイトを超える部分は隠して「⋯」を出す（VS Code の `stopRenderingLineAfter`）。1 行の巨大な JSON で固まらないため |

複数のキャレット、ミニマップ、LSP は入れない（今は）。折り返しは既定でしない（`wrap(true)` で折り返す）。

### 大きなファイル

構文木はソースの約 20 倍のメモリを使う。VS Code と同じく、20 MB を超えるファイルは色分けしない（`highlight_limit` で変えられる）。

### 速さ

素の `text_editor`、sqlite3.c（9.3 MB、262,899 行）、1000 × 900:

| | 前 | 後 |
|---|---|---|
| 作る | 1.4 秒 | 29 ms |
| メモリ（RssAnon） | 4.2 GB | 34 MB |
| ノード | 約 53 万 | 185 |
| 1 打鍵 | 84 ms | 0.14 ms |
| Enter（折り返しありで、累積を足し直す） | ― | 1.5 ms |

`code_editor`（色分けあり）、1000 × 900、拡大率 1.8（`tests/editor.rs` の `time_a_long_file`）:

| ファイル | 作る | 色が付くまで | 1 打鍵（中央値 / 最大） | Enter | 1 ページ下 |
|---|---|---|---|---|---|
| Rust 2,975 行（`text/editor.rs`） | 26 ms | 35 ms | 0.58 / 0.90 ms | 0.95 ms | 1.9 ms |

- 最大の時間は、解析用のスレッドに渡す文字列の写し（9 MB で約 1 ms）と、2 秒ごとに UI スレッドで試す 1 ms。
- 構文木のメモリは sqlite3.c で約 155 MB。

### ほかのエディタとの比較

ファイルを開いてから、新しいウィンドウの中の画面の変化の 97% が済むまでの時間（`grim` で毎秒約 25 枚撮る）と、起動で増えたプロセス全部の PSS。ShojiWM のウィンドウが開くアニメーション（約 0.5 秒）はどのアプリにも入っている。アプリごとに使い捨てのホームディレクトリを使い、3 回ずつ交互に測った。画面の出力は NVIDIA の dGPU（AntiWebUI は省電力のため AMD の内蔵 GPU で描くので、両方の Vulkan ドライバを読む。うち LLVM が 75 MB）。

| アプリ | 中身 | 2,975 行の Rust | メモリ | sqlite3.c | メモリ |
|---|---|---|---|---|---|
| AntiWebUI `code_editor` | ネイティブ（wgpu）、tree-sitter | 0.72〜0.84 秒 | 270〜276 MB | 0.82〜0.89 秒 | 446 MB |
| Kate 26.08 | Qt、KSyntaxHighlighting | 0.39〜0.42 秒 | 99〜116 MB | 0.42〜0.45 秒 | 144〜153 MB |
| Sublime Text 4215 | ネイティブ | 0.88〜0.92 秒（1 回だけ 5.3 秒） | 193〜195 MB | 1.26〜1.34 秒 | 207〜209 MB |
| Zed（stable） | ネイティブ（GPUI）、tree-sitter | 0.91〜1.05 秒 | 478〜516 MB | 0.93〜1.11 秒 | 873〜882 MB |
| gnome-text-editor | GTK 4、GtkSourceView | 1.84〜1.93 秒 | 327〜329 MB | 6.59〜6.75 秒 | 389〜390 MB |
| VS Code 1.142 | Electron | 2.06〜2.18 秒 | 1187〜1203 MB | 2.30〜2.40 秒 | 1363〜1489 MB |

- tree-sitter を使うもの（Zed）とは、速さが同じか少し速く、メモリは半分ほど。Chromium の上のもの（VS Code）より 3 倍速く、メモリは 4 分の 1。
- Kate がいちばん速く軽い。GPU のドライバを読まず、色分けも見えている所まで行ごとにする方法（構文木を持たない）なので、メモリに構文木の分がない。AntiWebUI のメモリの多くは GPU のドライバ（NVIDIA 約 100 MB、AMD の LLVM 約 75 MB）で、アプリ自身の分（ヒープ 15 MB、実行ファイル 14 MB）は小さい。

## 入れていないもの

- 複数のキャレット、ミニマップ、LSP、括弧の自動の閉じ。
- タブ文字の幅（今は parley の空白の幅）。Go のようにタブで字下げする言語では、字下げが狭く見える。
- 折りたたみの印を行番号の横に出すこと（今はキーと、たたんだ行の「⋯」だけ）。
- 長いファイルの色分けで、画面の位置から解析すること（今は開いたときの先頭だけ先に解析する）。
- Markdown のソースモード（`markdown_editor` から切り替える）。言語としての Markdown（コードブロックの中の言語を含む）はもう色が付く。
