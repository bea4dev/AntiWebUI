# 10. フレームの先行とフレーム計測

CPU が次のフレームを始められるのに、前のフレームの GPU 処理やコンポジタの受け取りを待って寝ている時間を減らす仕組み（いわゆるトリプルバッファリング）と、それを判断するためのフレーム計測。

## 計測

`ANTIWEBUI_FRAME_STATS=out.csv` を指定すると、どのアプリでも 1 フレームごとの時刻を CSV に書き、ウィンドウを閉じたときに集計を標準エラーに出す（`-` なら集計だけ）。

| 区間 | 求め方 |
|---|---|
| CPU の各工程（UI、差分、バッファ取得、記録、submit） | `CLOCK_MONOTONIC` |
| GPU の完了 | 描画完了の sync_file を `SYNC_IOC_FILE_INFO` で読む。カーネルが記録した signal 時刻 |
| 画面に出た時刻 | `wp_presentation_feedback.presented`。リフレッシュ周期もここから得る |
| 飛ばしたリフレッシュ | 連続して描いているフレームの、画面に出た間隔 ÷ リフレッシュ周期 − 1 |

- 「連続」は、始められるようになった（コールバックが来て、前のフレームの CPU 処理も終わった）直後に始めたフレームのこと。入力待ちの後のフレームの間隔は、描画の速さと関係ない。
- GPU の完了時刻はカーネルの仕組みで、メーカーごとの処理を持たない。NVIDIA でも同じ方法で読めるはずだが未確認で、値が無いドライバでは「不明」として扱う。AMD では、sync_file を `poll()` で待つスレッドが起きた時刻と比べて、記録された時刻の 0.3 ms 後（最大 1 ms）に起きることを確認した。
- この時刻には GPU のキュー待ちも含む。内蔵 GPU をコンポジタと共有していると、コンポジタの描画直後に submit したフレームは後ろに並ぶ。小さな描画で、すぐ submit すると 2.2 ms、4 ms 遅らせると 0.03 ms だった。
- `bench_pacing` は CPU 負荷（`--cpu-ms`）と GPU 負荷（`--layers`）を指定して動き続けるウィンドウ。

分かったこと:

- **普段の負荷では要らない**。実際のスクロールは CPU と GPU を合わせても 1 フレームに余裕で収まる。
- **効くのは、CPU と GPU はそれぞれ 1 フレームに収まるが合計すると収まらないとき**。この範囲では飛ばしが消え、代わりに遅延が 1 リフレッシュ（8.3 ms）増える。
- **片方だけで 1 フレームを超えているときはほとんど効かない**のに、遅延は増える。
- 1 フレームに使える時間はリフレッシュ周期より短い（CPU 7 ms だけで 471 フレーム中 37 回飛び、うち 35 回は CPU と GPU の合計が周期に収まっていた）。コンポジタ側の処理と締め切りがあるためと考えられる。余裕の割合はコンポジタと GPU で変わるので、閾値では判断しない。
- 負荷と効果の関係は実行ごとに揺れる（GPU 約 10 ms は、この環境の境界にある）。

## Chromium の方式

ソース（`ui/ozone/platform/wayland/host/wayland_frame_manager.cc`）と実際の動作の両方で確認した。

- 描き終わったフレームを `pending_frames_` に積み、前のフレームの `wl_frame_callback` が来てから次を commit する（`WaitForFrameCallback`）。
- `WAYLAND_DEBUG` のログでは、すべての負荷でコールバック待ちの間の commit が 0 回だった。

| 負荷（同じ内容のページ） | Chrome fps | AntiWebUI（Auto）fps |
|---|---|---|
| 小さな変更のみ | 119.7 | 117.8 |
| CPU 4 ms + 40 層 | 119.3 | 120 |
| 60 層 | 119.5 | 86.9 |
| 120 層 | 118.9 | 50.4 |
| CPU 7 ms | 119.5 | 113.7 |
| CPU 12 ms | 82.8 | 73.4 |

**訂正:** この表の層の行と CPU の行は、どちらも正しい比較になっていなかった。

- **層の行:** ベンチのアルファの変化が 8 ビットに丸めると同じ値になり、Chrome はほとんど描き直していなかった。正しい比較は `11-gpu-fill.md`。
- **CPU の行:** 保留中のフレームの commit を次のフレームの CPU 処理が終わるまで送っていないバグがあった（下の「commit はすぐ送る」）。修正後は CPU 7 ms で 115.6fps（Chrome 119.8）、CPU 12 ms で 80.7fps（Chrome 82.3）。電池駆動で、コンポジタの負荷が高い状態での測定。修正前は同じ条件で 60.0fps と 58.9fps だった。

上の「結果」の表も修正前の測定で、先行の効果を実際より低く示している。

## 方式

Chromium と同じく、**描画だけを先に進め、commit はコールバックを待つ**。

```
先行なし:
  callback → CPU → submit, commit →（寝る）→ callback → CPU …

先行あり:
  callback → 保留中のフレーム N を commit → フレーム N+1 の CPU → submit → 保留 →（寝る）→ callback → N+1 を commit …
                                             ↑ GPU はフレーム N を描いていてよい
```

- コンポジタから見ると 1 フレームごとに commit とコールバックが対応するだけで、Wayland コアの機能しか使わない。`wp_fifo_v1` や `wp_commit_timing_v1` は要らず、コンポジタと GPU を選ばない。
- 保留中のフレームは描画完了を待たずに commit する（完了は acquire 点で伝わる）。そのためフレームに使える時間が最大で 1 リフレッシュ増える。
- 入力の後の最初のフレームは、待つ相手が無いのですぐ commit する。**タイピングやクリックの遅延は変わらない**。
- 同時に保留できる数が `max_advance`。保留中は別のバッファを使うので、バッファの上限はその分だけ増える（`MAX_BUFFERS` + 保留数）。使わなければ確保しない。
- 空きバッファが無いときは、先行のためには待たない（UI スレッドを止めない）。

### commit はすぐ送る

保留中のフレームを commit したら、次のフレームを始める前に `wl_display_flush` する。コンポジタが受け付けるのはリフレッシュのある時点までで（高負荷の ShojiWM では、コールバックから約 6 ms）、CPU 処理の後に送ると間に合わない。`WAYLAND_DEBUG` のログには書き込んだ時刻が出るので、送っていないことはログからは分からない。

### 保留中のフレームの扱い

| 場面 | 動作 |
|---|---|
| ウィンドウの大きさやスケールが変わった（`Resized`） | 保留中のフレームを捨てる。古い大きさのバッファを、新しい configure の後に commit しないため |
| 捨てたときの変更範囲 | `unsent` に貯め、次の commit の `damage_buffer` に含める（コンポジタは捨てたフレームを見ていない）。内容に変化が無くても commit する |
| buffer age | 描いたフレームの順に数えるので、捨てても正しい。commit されていないバッファの release 点は進めない |
| ポップアップがあるとき | 先行しない。ウィンドウと歩調を合わせ、最新の内容を出すため |
| wgpu Surface（フォールバック） | 先行しない。commit が WSI の中にあり保留できない |

### 確認

- 実コンポジタで、保留あり（1 枚、3 枚）、暗黙的同期、保留の強制破棄（一時的なプローブで 7 フレームごと）の最後のフレームを、`grim` とダンプで比較し、差は 0 ピクセル（2617920 ピクセル中）。
- `WAYLAND_DEBUG` で、コールバック待ちの間の commit は 0 回、プロトコルエラーは 0。
- 判定ロジックは単体テストで確認し、15 個の変異をすべて検出。
- NVIDIA（コンポジタも NVIDIA）でも、dmabuf と明示的同期で動き、保留あり（1 枚、3 枚）と暗黙的同期の比較は差 0 ピクセル、コールバック待ちの間の commit は 0 回、プロトコルエラーは 0。sync_file の時刻も、`poll()` で待つスレッドが記録の 0.3〜0.4 ms 後（最大 1.4 ms）に起きることを確認した。小さなフレームでは GPU が submit の呼び出しより先に終わるので、`gpu` の区間が負になることがある。
- コンポジタが NVIDIA のとき、wgpu Surface のフォールバックは省電力を優先して AMD で描く。この組み合わせでも動く。

## 設定

```rust
App::new()
    .settings(|s| s.rendering.frame_advance = FrameAdvance::Auto)
    .run(root)?;
```

| 値 | 動作 |
|---|---|
| `Auto`（既定） | 効果があるときだけ 1 フレーム先行する |
| `Enable` | 連続して描く間は常に 1 フレーム先行する |
| `Disable` | 先行しない。遅延は最小で、間に合わないフレームは飛ぶ |
| `Custom { max_advance }` | 連続して描く間は最大でこの枚数先行する。0 は `Disable` と同じ。4 より大きい値は 4 として扱う |

環境変数 `ANTIWEBUI_FRAME_ADVANCE=auto|on|off|数値` で、プログラムを変えずに上書きできる（計測と切り分け用）。

## Auto の判定

GPU とコンポジタの組み合わせごとに閾値を調整しなくて済むよう、**予測せず試す**。NVIDIA dGPU、ハイブリッド構成、別のコンポジタでも同じ判定で動く。

```
Off ──直近 32 フレームで 4 回以上飛んだ──▶ Trying
Trying（落ち着いた後）──32 フレーム後、平均間隔が 1.1 倍以上速い──▶ On
Trying（連続の始め）──16 フレーム後、1.5 倍以上速い──▶ On
Trying（連続の始め）──1.1〜1.5 倍──▶ Off（連続が 64 フレームを超えてから試し直す）
Trying ──1.1 倍未満──▶ Unhelpful（8 秒、効かないたびに倍、最大 64 秒）──▶ Off と同じ判定に戻る
On ──描いている間の合計 2 秒、続けてリフレッシュの 50% に収まった──▶ Off（5 秒以内に戻ったら待ち時間を倍、最大 16 秒）
```

- 一時停止（フレームの間隔が 100 ms 超）の後、最初の 4 フレームは見ない。ウィンドウの表示や一時停止の直後は、どの負荷でも数フレーム遅い。少し遅れて始まっただけのフレームは一時停止として扱わない。
- **立ち上がりを短くする:** 重い負荷では、飛びを 4 回見たらすぐ試す。60fps に落ちている負荷なら、フレームが揃うまで 8 フレーム（約 130 ms）と、結果が返るまでの数フレームで先行に入る。
- **連続の始めの判定は厳しくする:** 始めの方はどのモードでも遅いので、効果を過大評価してしまう（実測では、起動直後の窓で平均 16 ms、その後は 12 ms で、1.33 倍の差）。そのため連続が 64 フレームに満たない間は 1.5 倍を基準にする。はっきり効くときだけすぐ採用し、微妙なときは落ち着いてから通常の基準で確かめる。連続の始めの試行は、記憶を捨てるまでに 1 回だけ。
- **On は一時停止で忘れない。** アプリの負荷は急には変わらないので、次のアニメーションは最初から先行する。一時停止の後の最初のフレームは待つ相手が無いのですぐ commit するので、クリックやタイピングの遅延は増えない。
- **戻すのは明らかに余裕があるときだけ。** 実測では CPU 5〜6 ms で飛び始めるので、70% の基準（5.8 ms）はその境目にあり、先行の入り切りを繰り返しかねない。50%（4.2 ms）にした。
- 余裕の時間は描いている間だけ数える。一時停止の時間は数えず、再開の直後の 4 フレームも見ない。1 回でも基準を超えたらやり直す。
- 比べる間隔は 4 リフレッシュで頭打ちにする。たまの大きな止まりで平均が動かないように。
- 5 秒以上フレームが無ければ、「効かなかった」という記憶は捨てる（負荷が変わっているかもしれず、試すのは短い）。
- `wp_presentation` が無い、またはリフレッシュ周期が 0（VRR）のときは飛ばしを判定できないので、Auto は先行しない。`Enable` と `Custom` は使える。

- 1000 層は間隔が比較の上限（4 リフレッシュ）に当たるので、効果が見えず先行しない。遅延が 36 ms 増えないので、むしろ都合がよい。

代償:

- 試す間の 32 フレーム（120 Hz で約 0.3 秒）は、効かなくても遅延が増える。
- `On` の間に負荷が変わって効かなくなっても、70% に収まるまでは `On` のまま。遅延が増えるだけで、表示は崩れない。

## スレッド

**スレッドは増やしていない。** すべて UI スレッドで動くので、利用者のコードにロックは要らない。`signal` も `request_frame` のクロージャも `Send` である必要は無い。

計測では、記録と submit は合わせて 0.2〜0.6 ms だった（2000 行のスクロールで 0.17 ms、8.33 ms の周期に対して 2%）。描画を別スレッドに移しても得られる時間が少ないため、今回は見送った。

もしコールバックが来たときに UI スレッドが作業中でも、保留中のフレームの commit はその作業が終わるまで遅れるだけで、表示は崩れない。これが問題になる負荷（UI の作業が 1 リフレッシュを超える）では、CPU 12 ms の測定のとおり Chrome より約 10% 遅い。将来、表示スレッドを分ける場合も内部の変更で、利用者から見て UI スレッドは 1 本のままにする。

## 毎フレームの処理

`request_frame(|now| …)` は `requestAnimationFrame` に当たる。次のフレームを作る前に UI スレッドで 1 回呼ばれ、中でもう一度呼ぶと毎フレーム動き続ける。多くの場合は `transition` や `animated` の方が手軽（[13](13-animation.md)）。

```rust
fn spin(angle: Signal<f32>) {
    request_frame(move |_| {
        angle.update(|a| *a += 1.0);
        spin(angle);
    });
}
```

`now` は表示予定の時刻ではなく、フレームを作り始めた時刻。表示予定の時刻（vblank の格子に揃えた時刻）も実装して比べたが、予測が 1 リフレッシュ分外れることがあり、動きの誤差は改善しなかったので採用していない（RMS で、小さな変更のみ 1.17 ms → 2.38 ms、CPU 4 ms + 40 層の先行中 0.76 ms → 0.71 ms）。先行中は開始時刻がコールバックに揃うので、それだけで誤差が小さくなる（off 3.99 ms → on 0.76 ms）。
