# 05. レンダラ（anti-webui-wgpu）

## 入力: Scene

core はフレームごとに `Scene`（描画コマンドの列）を生成する。座標は物理 px。

```rust
enum Primitive {
    Shadow(Shadow),      // ボックスシャドウ（外側・内側）
    Quad(Quad),          // 背景・枠線・角丸・キャレット・選択ハイライト・下線
    Glyphs(GlyphRun),    // フォント参照・サイズ・座標・色
}
```

どのプリミティブも自分のクリップ矩形を持つ（push/pop 型のクリップスタックは使わない）。

- `Quad`: 整数矩形、背景色、辺ごとの枠線幅（整数）、枠線色、4 隅の角丸半径（f32）。
- `Shadow`: ぼかす形（矩形と半径）、ぼかし、色、切り抜く形（[09](09-shadows-stacking-popups.md)）。
- `GlyphRun`: フォントデータ（`Blob` + index）、物理フォントサイズ、正規化座標（可変フォント）、合成（太字・斜体）、色、各グリフの `(id, x, y)`。

## GPU 側

- **矩形パイプライン**: インスタンス描画。フラグメントシェーダで角丸矩形の SDF を評価し、枠線と背景を 1 パスで描く。影も同じパイプラインで、箱の内側を除いた最大 4 枚の四角形として描く（[09](09-shadows-stacking-popups.md)）。
- **グリフパイプライン**: インスタンス描画。RGBA8 アトラス 1 枚。単色グリフはカバレッジを、カラー絵文字はプリマルチプライド色を格納し、インスタンスのフラグで区別する。
- **クリップ**: インスタンスごとにクリップ矩形を持たせ、シェーダで判定する（バッチを分けずに済む）。
- **順序**: Scene の順に、同じパイプラインが続く区間を 1 ドローコールにまとめる。
- **ブレンド**: プリマルチプライドアルファ。ブラウザと同じくガンマ空間（非 sRGB フォーマット）で合成する。

## グリフキャッシュ

- キー: `(フォント blob id, フォント index, グリフ id, 物理サイズ（1/64 px 量子化）, サブピクセル x（1/4 px）, 合成フラグ, 可変フォント座標のハッシュ)`。
- ラスタライズは swash。ソース優先順: カラーアウトライン → カラービットマップ → アウトライン。
- アトラスはシェルフパッキング。満杯になったら拡張し、それでも足りなければクリアして次フレームで再構築する。

## ダメージトラッキング

変更された領域だけを描き直し、その範囲を OS のコンポジタにも伝える。Chromium と同等の効率を目標にする。

### 1. 変更領域を求める（core）

- ペイントは Scene を**チャンク**に区切って出力する。チャンクは「あるノードのある部分」を表すキー `ChunkKey(node, part)` と、連続するプリミティブの範囲を持つ（Chromium の PaintChunk に相当）。
  - `part` は「自身の背景・テキスト」「子の後に描くもの（スクロールバー・アウトライン）」「キャレット」を区別する。キャレットを独立させることで、点滅のたびに入力欄全体が汚れるのを防ぐ。
- 前フレームの Scene と比較して変更矩形を求める（`damage::diff`）。
  1. 新しいチャンクを順に、前フレームの同じキーのチャンクと対応付ける。
  2. 対応が無い（追加）→ 新しい範囲を汚す。前フレームにしか無い（削除）→ 古い範囲を汚す。
  3. 対応があり、前フレームでの並び順が逆転している → 両方の範囲を汚す（重なりの描画順が変わるため）。
  4. 内容が異なる → プリミティブ数が同じなら、異なるプリミティブの新旧の範囲だけを汚す。数が違えばチャンク全体の新旧の範囲を汚す。
- 画面サイズや背景色（clear）が変わったら全面を汚す。
- **正しさ**: 汚れていないピクセルは、同じ内容・同じ相対順序のプリミティブだけで覆われるので、前フレームと同じ結果になる。
- プリミティブの範囲:
  - 矩形: `rect ∩ clip`（アンチエイリアスは矩形の内側で完結する）。
  - 影: `blur × 1.5 + 1`（3σ と端の 1 px）だけ外側に広げる。内側の影はパディングボックスの中。
  - グリフ: フォントの `head` テーブルの外接矩形（全グリフを包む）にグリフ位置を足して求める。合成太字・斜体・サブピクセル位置の分の余白を加える。
- 矩形が多すぎると GPU 側のコストが増えるので、重なる矩形や、併合しても無駄な面積が小さい矩形をまとめ、最大 8 個に抑える。

### 2. 部分描画（renderer）

- `Renderer::render_damaged(…, damage)` は、描画先の内容が「前回までの正しいフレーム」である前提で、変更矩形の中だけを描き直す。
  - `LoadOp::Load` で前の内容を残す。
  - 矩形ごとに scissor を設定し、ブレンド無しのパイプラインで clear 色を塗ってから、その矩形に掛かるプリミティブを描く。
  - どの矩形にも掛からないプリミティブは、インスタンスを作る段階で捨てる。
- **buffer age**: 表示用バッファは複数枚を順番に使うため、あるバッファの中身は「k フレーム前」のものである。描き直す範囲は、直近 k フレーム分の変更矩形の和にする（`DamageHistory`）。age が分からないバッファは全面を描く。
- 変更矩形が空なら、そのフレームは描画も提示もしない。

### 3. 提示とコンポジタへの通知（presenter）

wgpu の Surface は buffer age も変更範囲の通知も公開していないので、OS ごとに表示用バッファを自前で管理する presenter を持つ。core と renderer は共通で、presenter だけが OS ごとに異なる。

| OS | バッファ | 変更範囲の通知 | 状態 |
|---|---|---|---|
| Wayland | dmabuf を自前で確保（Vulkan） | `wl_surface.damage_buffer` | 実装（[06](06-platform-wayland.md)） |
| Windows | DXGI flip model のバッファ / DirectComposition | `Present1` の dirty rects、`IDCompositionSurface::BeginDraw` | M3 |
| macOS | IOSurface を自前で回し `CALayer.contents` に設定 | 矩形単位の API は無い。減るのは GPU の仕事だけで、合成は層の単位（レイヤー分割は今後） | 実装（[37](37-platform-macos.md)） |
| その他 / フォールバック | wgpu Surface | 無し（毎回全面） | 実装 |

ポップアップも同じ構成で、バッファと履歴をサーフェスごとに持ち、GPU デバイスとレンダラは共有する（[09](09-shadows-stacking-popups.md)）。

自前管理ができない環境（GL バックエンド、dmabuf 非対応のコンポジタなど）では、wgpu Surface に全面描画するフォールバックを使う。この場合も「変更が無ければ描かない」は効く。

## スクロールレイヤー

スクロールだけのフレームでは内容が変わらない。そこで、スクロール内容を描いたテクスチャと描画リストを保持し、動いた分だけ処理する。計測（2000 行のリスト、1 ステップ）では GPU より CPU の方が重かった（ペイント 3.07 ms、記録 15.26 ms、GPU 待ち 1.09 ms）ので、**CPU 側の処理を省くこと**も同じくらい重視する。

### Scene の構造

- `overflow: scroll` で実際にはみ出している要素のうち、最も外側のものを `Primitive::Layer(Layer)` にする。`transform` も同じ仕組みを使う（[12](12-transform.md)）。
  - `content: Arc<Scene>`: スクロール内容の描画リスト。座標は**コンテンツ座標**（スクロール量に依存しない）で、クリップもレイヤー自身と祖先のものを含まない。
  - `origin`: コンテンツ座標の原点のウィンドウ上の位置。スクロールで変わるのはここだけ。
  - `clip`: レイヤーを表示する範囲（ウィンドウ座標、角丸あり）。
- 入れ子のスクロール要素は外側の内容の一部として描く。内側をスクロールすると外側の該当範囲だけが描き直される（差分計算がそのまま効く）。
- スクロールバーと、スクロール要素自身の背景はレイヤーの外（ウィンドウ側）に描く。

### ペイントの省略

- ダーティフラグに `content`（描画内容が古い）を追加する。スタイル・レイアウト・描画のどの変更でも立つが、最も外側のスクロール要素のスクロールでは立たない。
- `content` が立っていなければ、前回の `Arc<Scene>` をそのまま使い、スクロール内容のペイントと差分計算を丸ごと省く（`Arc` のポインタが同じなら内容も同じ）。

### テクスチャ（トーラス）

レイヤーごとに、表示範囲以上の大きさのテクスチャを 1 枚持ち、**コンテンツ座標を幅・高さで割った余りの位置**に描く。上下左右どの方向に動いても、すでに描いた部分はテクスチャ上で動かない。

```
texel = (content.x mod 幅, content.y mod 高さ)
```

- 描き直す範囲 = （今の表示範囲 − 前回から残っている範囲）∪（内容の差分 ∩ 残っている範囲）。
- テクスチャの端をまたぐ矩形は最大 4 つに分けて描く。合成も同じく最大 4 枚の四角形になる。
- タイルと比べて: 使用メモリが表示範囲 1 枚分で一定、タイルの管理が要らない。一方で、遠くへ移動してから戻ると描き直しになる（表示範囲外は保持しない）。
- 再描画はスクロール量に比例する。ジャンプなどで表示範囲がすべて入れ替わるときは、従来の全面描画と同じコストになる。
- シーンから消えたレイヤーのテクスチャはすぐ解放する。

### 合成

- ニアレストサンプリングで、スクロール量は物理 px の整数なので、テクスチャのピクセルがそのまま画面のピクセルになる（にじまない）。
- プリマルチプライドの内容を透明の上に描いてから合成する。式の上では直接描くのと同じだが、8bit の丸めで ±1 の差が出ることがある。
- レイヤーの原点が変わったら表示範囲全体を変更矩形にする（ピクセルは実際に変わるので、コンポジタへの通知はこれ以上狭くならない）。

### 効果

`bench_scroll`（2000 行のリスト、1620×1616、Radeon 880M、1 ステップあたり）:

| 処理 | レイヤー導入前 | 導入後 |
|---|---|---|
| ペイント | 3.07 ms | 0.00 ms |
| 差分計算 | 0.75 ms | 0.00 ms |
| 描画の記録 | 15.26 ms | 0.05 ms |
| GPU 待ち | 1.09 ms | 0.19 ms |

代わりに、レイヤーごとに表示範囲 1 枚分の GPU メモリを使う（1620×1500 で約 10 MB）。

### 効かない場合

- ズーム（描き直しになる。将来ズームを入れるなら低解像度の一時表示が要る）。
- スクロールと同時に内容も変わる場合（変わった範囲は描き直す）。

## CPU 側の差分化

`bench_changes`（20000 行、4 万ノード）で、ホバー 1 回に 70 ms かかっていた（ペイント 31、スタイル解決 19、差分 8、記録 8、ヒットテスト 4）。GPU は 1 ms 未満で、残りはすべて全ノードの走査だった。処理量を「変わった部分＋見えている部分」に比例させる。

### スタイル解決: 変わったノードだけ

- 無効化はノード単位にする（`mark_style_of(id)`）。ホバー・押下・フォーカスは、実際にそのスタイルを持つノードだけを無効化する。
- 解決は無効化されたノードから始め、計算結果が変わったときだけ子へ進む（子の入力は親の計算結果と自分のスタイルだけなので、変わらなければ子も変わらない）。
- 多数のノードが無効なとき（起動時など）と、スケールが変わったときは全体を解決する。

### 座標空間: スクロールで座標を書き換えない

- スクロール内容（はみ出している最も外側のスクロール要素の子孫）の `Node::abs` と `Node::clip` は**その要素のコンテンツ座標**で持つ。
- スクロールしても書き換えるものが無いので、位置計算自体が要らない。スクロール量を変えるだけになる。
- ウィンドウ座標が要る箇所（ヒットテスト、ポインタイベント、IME のカーソル位置、`NodeRef::rect`）は `Document::window_rect` などで変換する。
- 入れ子のスクロール要素のスクロールは、その子孫だけ位置を計算し直す。

### 位置計算: 動いていない部分木は飛ばす

レイアウト後の位置計算では、レイアウトをやり直していないノードで位置・クリップ・文書順が同じなら、部分木を丸ごと飛ばす。

### ペイント: 見える範囲だけ

- 各ノードは**部分木の描画範囲**（`subtree_bounds`: 自身の枠、影、アウトライン、テキストのはみ出し、子孫の範囲。クリップする要素では切り詰める）を持ち、親は子の範囲を詰めた配列（`child_bounds`）で持つ。
- ペイントは**カリング矩形**と交わらない子を見ない。ヒットテストも同じ配列で枝刈りする。ノード本体に触らないので、キャッシュミスも起きない。
- カリング矩形は、ウィンドウでは画面、レイヤーでは表示範囲を上下左右に画面 1 枚分広げたもの。表示範囲がそこから出るまでは描画リストを再利用する。
- レイアウトを伴わずに影やアウトラインが変わったときは、祖先の範囲を広げる（縮める方は次の位置計算まで保守的なまま）。

レイヤーの描画リストが見える範囲だけになるので、差分計算と描画の記録も自動的に小さくなる。

### 効果

`bench_changes`（1620×1616、Radeon 880M、1 回あたり）:

| 操作 | 20000 行・導入前 | 20000 行・導入後 | 2000 行・導入後 |
|---|---|---|---|
| ホバー | 70.41 ms | 0.45 ms | 0.38 ms |
| キャレットの点滅 | 46.40 ms | 0.29 ms | 0.26 ms |
| テキストの変更 | 54.74 ms | 3.72 ms | 0.71 ms |
| スクロール（行にホバーあり） | 67.46 ms | 0.48 ms | 0.41 ms |

### 正しさの確認

差分更新は更新漏れが起きやすいので、`tests/incremental.rs` で次を確かめている。

- ランダムな操作（ポインタ、スクロール、スタイル、文字、キーつきリストの増減と並べ替え、表示切替、リサイズ、スケール変更）のたびに、全ノードの状態と Scene が、すべてやり直した結果と一致する。
- カリングしたペイントと、カリングしないペイントが、見える範囲で同じプリミティブ列になる。
- ヒットテストと選択の結果が、全ノードを見る素朴な実装と一致する。

### 残るコスト

- レイアウトは、変更があったノードの祖先の子を全部見る（2 万行の親の下でテキストが変わると 2 万回のループで、約 3 ms）。各子の計算はキャッシュが効くが、走査は残る。サイズが変わらない変更で親のレイアウトを省く仕組み（Chromium の simplified layout に相当）で解消できる。
- 内容が変わるとレイヤーの差分計算は presenter とレンダラの 2 か所で走る。描画リストが見える範囲だけになったので、今は問題にならない。
- 全選択とコピーは全ノードを見る（ユーザー操作の頻度なので問題にならない）。

## 表示

- サーフェス形式は `Bgra8Unorm` / `Rgba8Unorm`（非 sRGB）を優先。
- バックエンドはまず Vulkan / Metal / DX12 を試し、アダプタが無いときだけ GL に落ちる（Mesa の GL は LLVM を読み込むため重い）。環境変数 `WGPU_BACKEND` で上書きできる。
- PresentMode は `Mailbox` → `Fifo` の順で選ぶ。フレームの律速は Wayland のフレームコールバックで行う（非表示ウィンドウで WSI がブロックするのを避ける）。
- オフスクリーン描画（テクスチャ → PNG）をサポートし、テストとスクリーンショットに使う。

## デバッグ

- `ANTIWEBUI_DEBUG_DAMAGE=1` を指定すると、フレームごとに変更矩形・buffer age・描き直した面積の割合を標準エラーに出す。
- `ANTIWEBUI_FRAME_STATS=out.csv` を指定すると、CPU の各工程、GPU の完了、画面に出た時刻をフレームごとに記録する（[10](10-frame-pacing.md)）。
- `ANTIWEBUI_PRESENT=surface` で、自前の presenter を使わず wgpu Surface（全面描画）に固定する。

- `ANTIWEBUI_DUMP_FRAME=out.png` を指定すると、表示したフレームと同じ Scene をオフスクリーンで描画して PNG に書き出す（画面キャプチャ無しで実バッファの内容を確認できる）。
- `anti_webui_app::headless::{render_png, render_driven_rgba}` で、合成イベントを流した後の状態をスナップショットにできる。
