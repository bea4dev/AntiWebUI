# 28. Markdown

Markdown のビュワーと、Obsidian のライブプレビューのように書けるエディタ。Mermaid の図も描く。目標は最速・最軽量で、同じ文書を Chromium で開いたときと速さとメモリを比べる。

Web で Markdown エディタを作るときと同じく、基礎の部品を core に置き、それを組み合わせて Markdown の部品を作る。基礎の部品は Markdown 以外（チャット欄、コードエディタ、カスタム絵文字の入力欄）にも使える。

## 構成

| 置き場所 | もの |
|---|---|
| `anti-webui-core` | `rich_text`（`span`、`inline`）、`text_editor`（行ごとの整形、装飾、見えている行だけの整形） |
| `anti-webui-markdown` | `markdown_view`、`markdown_editor`、Mermaid（feature `mermaid`） |

パーサ（`pulldown-cmark`）と Mermaid は `anti-webui-markdown` だけが持ち、core には入らない。

## 段階

| 段階 | 中身 |
|---|---|
| M1 | core: `rich_text` |
| M2 | markdown: `markdown_view`（CommonMark と GFM）、Mermaid |
| M3 | core: `text_editor` |
| M4 | markdown: `markdown_editor`（ライブプレビュー） |

ソースをそのまま書くモード（Markdown 用のコードエディタ）は後回しにし、コードエディタとして別に作る。その土台も M3 の `text_editor` になる。

## M1: `rich_text`

1 つの段落の中で文字のスタイルを変えたり、文字の間に画像などのノードを置いたりする。HTML の `<p>` の中の `<strong>`、`<code>`、`<a>`、`<img>` に当たる。

```rust
rich_text((
    "これは ",
    span("太字").bold(),
    " と ",
    span("code").font_family("monospace").bg(code_bg).rounded(4.0).px(3.0),
    " と ",
    inline(img("party.png").w(20.0).h(20.0)).alt(":party:"),
    " と ",
    span("リンク").text_color(link).hover(|s| s.underline()).on_click(|| open(url)),
))
.text_size(16.0)
```

`span` は `Styled` を持つので、`div` と同じメソッド（`bold`、`italic`、`text_color`、`text_size`、`bg`、`rounded`、`px`、`underline`、`cursor` など）が使える。テーマのように多くの `span` が同じスタイルを使うときは、`shared_style(Rc<Style>)` で 1 つのスタイルを共有できる。`vertical_align(VerticalAlign::Super)` で上付きにする。

### 持ち方

- 段落全体が今までと同じ 1 つのテキストノード（`NodeKind::Text`）である。そのため、文書全体の選択、ダブルクリック、コピー、文字を運ぶ操作がそのまま効く。
- `span` はノードにしない。ノードはスタイルの計算結果などを持っていて重いので、範囲とスタイルの差分だけを `TextData` の `rich` に持つ。`rich` は普通のテキストでは `None` なので、普通のテキストは重くならない。
- `span` は重ならず、並んでいるだけである（入れ子にしない）。入れ子にしたいもの（`**太字の _斜体_**`）は、作る側が重ねたスタイルを持つ `span` に分ける。
- `span` が変えられるのは、文字に関するものだけである。
  - 整形が変わるもの: `font_family`、`font_size`、`font_weight`、`font_style`、`letter_spacing`
  - 描くときだけのもの: `color`、`bg`、`rounded`、`underline`、`strikethrough`
- 左右の余白（`px`、`pl`、`pr`）だけは整形にかかわる。`span` の両端に高さ 0 のインラインボックスを置いて空けるので、CSS の `padding-inline` と同じく、背景の内側に余白ができる。
- `line_height` が倍率のときは、CSS と同じく `span` の文字サイズに対する倍率になる。大きい `span` があると、その行が高くなる。
- `span` のスタイルは、ノードのスタイルが決まるとき（`resolve_styles`）に、ノードのスタイルから受け継ぐものと合わせて解決し、持っておく。整形が変わらない変更（色など）では整形し直さない。
- 整形のキャッシュの鍵には、文字列の版に加えて、インラインボックスの大きさを入れる。

### 背景

背景は、`span` の文字の範囲を行ごとに求め、縦はフォントの ascent から descent までとする。CSS のインライン要素の背景と同じく、`line-height` を大きくしても背景は高くならない。行をまたぐ `span` は、行ごとに別の箱になる（`box-decoration-break: slice` の角は付けず、それぞれ角を丸める）。

### インラインボックス

- `inline(view)` の中身は parley の `InlineBox` として行に流し込む。文字列に代わりの文字は入れず、位置（バイト）だけを持つ。
- 中身は、段落が使える幅の中で max-content の大きさを測ってから整形する。行の中での位置が決まったら、中身をその位置に置く。中身はテキストノードの子なので、描画、当たり判定、画像の読み込みは普通のノードと同じである。
- 縦の位置は `VerticalAlign`（`Baseline`（既定）、`Middle`、`Top`、`Bottom`、`TextTop`、`TextBottom`）で決める。
- コピーしたときは、選択範囲に含まれるインラインボックスの `alt` を、その位置に入れる。

### リンクとホバー

- `on_click` を持つ `span` は、押して同じ `span` の上で離したときに呼ばれる。
- `span` の `cursor` は、その `span` の上にいる間のカーソルになる。`on_click` があるときの既定は `Pointer` である。
- `hover` で変えられるのは描くときだけのスタイルで、整形はやり直さない。

### 入れないもの

- `span` の入れ子、`span` ごとのシグナル（段落全体を `dyn_view` で作り直す）
- 選択範囲がインラインボックスの中身（画像の中のテキストなど）をまたぐときの正しい順番

## M2: `markdown_view`

```rust
markdown_view(source)                     // &str / String / Signal<String>
    .theme(MarkdownTheme::default())
    .on_link(|url| open(url))
    .image(|src| resolve(src))            // 相対パスの解決
    .emoji(|name| custom_emoji(name))     // ":party:" → Option<ImageSource>
    .highlight(|lang, code| spans)        // コードの色分け（既定はなし）
```

- パーサは `pulldown-cmark`。速く、要素ごとにソースのバイト位置を返す。GFM の表、タスクリスト、取り消し線、脚注を有効にする。
- 解析した結果を軽いブロックの列にし、それを普通のノードにする。
  - 見出しと段落は `rich_text`
  - リストは flex
  - 表は grid
  - 引用は左に線のある箱
  - コードブロックは `rich_text`
  - 区切り線は高さのある箱
- テーマは要素ごとの `Style` で、CSS で書くときと同じ感覚で当てられる。既定のテーマは GitHub の見た目に近づける。
- ソースが変わったときは、ブロックごとにソースの文字列を比べ、変わったブロックだけを作り直す。
- コードの色分けは重い依存（`syntect` など）を持ち込まないように、関数を渡すだけにする。色分けは後で作るコードエディタの側で用意する。

### 表

core にはまだ表のレイアウトがないので、表を列の並びとして作る。列は一番広いセルの幅になる。セルの中は折り返さず、表が広すぎるときは横にスクロールする（GitHub と同じ）。

`code` のように別のフォントの部分があると、行が少し高くなることがある。そのため、各セルの大きさを `on_resized` で受け取り、同じ行のセルの高さを一番高いセルに揃える。揃えるのは描く前なので、ずれた絵は出ない。

### HTML

ブラウザがないので、HTML のブロックは、文字、画像（`<img src alt>`）、リンク（`<a href>`）、改行だけを出す。README によくある `<p align="center">` は中央に寄せる。

### Mermaid

- 言語が `mermaid` のコードブロックを図にする。`merman` で SVG の文字列にし、`svg::parse` でノードにする。
- 図を作るのは 1 本のワーカースレッド（`markdown-diagrams`）で、出来たものはソースのハッシュで 64 個まで覚えておく。作っている間は空の箱を出しておく。
- feature `mermaid`（既定で有効）で外せる。
- `merman` は alpha 版で API がよく変わるので、`=0.10.0-alpha.1` に固定している。上げるときは `src/mermaid/merman.rs` と、下の比較を見直す。

#### クレートの選択

7 つのクレートを比べた（38 個のノードのフローチャートと、シーケンス図。リリースビルド）。

| クレート | 依存 | バイナリ | フローチャート | 文字幅を測る口 |
|---|---|---|---|---|
| `merman` | 122 | +25.2 MB | 2.7 ms | あり（クロージャ、トレイト） |
| `ariel-rs` | 19 | +2.5 MB | 2.8 ms | `fidelity` feature の `set_measurer` |
| `mermaid-rs-renderer` | 33 | +5.2 MB | 184 ms | なし（システムのフォントを読む） |
| mermaid-little | 46 | +8 MB | 34.5 ms | C の関数のコールバック |

最初は軽さを優先して `ariel-rs` を選んだ。その後、「最軽量」は Chromium より軽いことと決まったので、`ariel-rs` と `merman` を、Chromium で描いた mermaid.js 12.3 と比べ直した（2026-11-06）。図は 9 種類 11 個（フローチャート 2、シーケンス 2、クラス、状態、ER、ガント、円グラフ、マインドマップ、Git）。見た目が mermaid.js にずっと近く、それでも Chromium よりはるかに軽い `merman` に切り替え、`ariel-rs` は外した。

| | Chromium（mermaid.js 12.3） | `merman` | `ariel-rs` |
|---|---|---|---|
| バイナリ（strip 後、デモ全体） | 329 MB（本体） | 44.9 MB | 21.9 MB |
| メモリ（PSS、全プロセス、図なし → 11 個） | 530 → 665 MB | 64 → 133 MB | 62 → 105 MB |
| 11 個を描く時間（作る + ノードにして描く。バッテリー駆動） | 1 回目 877 ms、2 回目から約 390 ms | 1 回目 50 ms、2 回目から 43 ms | 1 回目 19 ms、2 回目から 15 ms |

時間はバッテリー駆動で続けて測った比で、電源につないで測り直すと絶対値は変わる（`ariel-rs` は電源につないだときの約 85 %）。

見た目（mermaid.js 12.3 と並べて目で比べた）:

| 図 | `merman` | `ariel-rs` |
|---|---|---|
| フローチャート | ほぼ同じ（大きさ、テーマ、配置）。線の曲げ方が違う。幅 120 をわずかに超えるラベルは 2 行になる（Chromium は折り返さず、箱の端で切れる。箱の大きさは同じ） | mermaid 11 のクラシックのテーマ。小さめ |
| シーケンス | ほぼ同じ | クラシック |
| クラス | 配置は同じ（矢じりと太字は下の修正で同じになった） | クラシック |
| 状態 | 配置が少し違う | 配置が違う |
| ER | ほぼ同じ | クラシック |
| ガント | ほぼ同じ | とても小さく読めない |
| 円グラフ | 同じ | 同じ |
| マインドマップ | 同じ（`layout-cytoscape`） | 配置が違う |
| Git | コミット名が回転しない（両方とも。`svg::text` が回転しないため） | 同じ |

比べる中で直した core の不具合:

- `width="100%"` の `<svg>` を、`max-width` までの幅にし、高さを縦横比から決める（ブラウザと同じ）。前は高さが元のままで、幅だけ縮んで上下に余白ができていた。
- ぼかしのない `feDropShadow`（mermaid 12 の箱の影）を、同じ形を影の色でずらして描く。前は図全体を 1 枚の絵にしていた。
- 図全体を 1 枚の絵にするときに、取り出した文字を絵からも消す。前は文字が二重になっていた。
- 隙間がすべて 0 の破線（Mermaid の線の `0 0 65 0`）を実線として描き、端が平らなときは長さ 0 の線を捨てる（`anti-webui-wgpu` の `dashes_to_stroke`）。kurbo に渡すと輪郭が壊れて黒い箱になっていた。
- 属性の始まり、終わり、中身で選ぶセレクタ（`[id$="-extensionEnd"]` など、`^=`、`$=`、`*=`）を、ファイルの中でそれに当たる値ごとの `[id="…"]` に書き換えてから `usvg` に渡す。`usvg` のスタイルシート（simplecss）はこれを知らず、並んだセレクタごと規則を捨てるので、クラス図の継承の矢じりが白抜きにならなかった。
- HTML のラベルの `font-weight: bolder` と `lighter` を、CSS の表どおり受け継いだ太さから決める。クラス名が太字にならなかった。

残っている違い: Git のコミット名が回転しない。`svg::text` は、まわりの変形の回転を無視して、点の位置だけを移す。回すには、変形のレイヤー（[12](12-transform.md)）を使うことになる。

#### 文字幅

`merman` の `DeterministicTextMeasurer` に、幅を測るクロージャ（`with_width_callback`）を渡し、ワーカースレッドでも core の `svg::measure_text` で測る。フォントの指定（`"Recursive Variable",arial,sans-serif` など）、太さ、斜体は `merman` の `TextStyle` から取る。ワーカースレッドは自分のテキストシステムを持つ（初めの 1 回だけ約 15 ms かかる）。

#### SVG の文字

今までの `svg::parse` は、`<text>` を `usvg` に組ませるために、そのたびにシステムのフォントを全部読み込んでいた（`svg-text` feature）。Mermaid の `<text>` は、ほとんどが点に置く 1 行の文字（`tspan` の入れ子と `x`、`y`、`dy` を含む）だけなので、foreignObject のラベルと同じく、取り出して目印の矩形に置き換え、`svg::text` として描くようにした。位置と変換は `usvg` が解いた目印から取る。1 行の中で文字ごとに位置を変えるもの、パスに沿うもの、途中でスタイルが変わるものは、今までどおり `usvg` に任せる。システムのフォントを読むのは、そういう `<text>` が残るときだけになる。

## M3: `text_editor`

ライブプレビューと、後で作るコードエディタの土台になる。大きな文書でも 1 打鍵が軽いことを最優先にする。

- **持ち方:** 文字列と行頭の位置の表を持つ。整形は行（段落）ごとで、変わった行だけを整形し直す。
- **見えている行だけを整形する:** まだ整形していない行は高さを見積もっておき、整形したら本当の高さに差し替える（CodeMirror の height map と同じ考え方）。
- **装飾:**
  - `mark`: 範囲のスタイル
  - `replace`: 範囲を隠す、またはノードに見せる
  - `widget`: 行の幅いっぱいのノード
  - `line`: 行の箱のスタイル（左の余白、背景、左の線）
- **表示用の文字列:** 行ごとに、隠す範囲を除き、IME の未確定文字列を入れたものを作り、元の位置との対応を持つ。今の `EditData` の `to_display` / `to_model` を一般にしたものである。
- **今の `text_area` から引き継ぐもの:** 取り消し、IME、クリップボード、文字を運ぶ操作。上下の移動は行をまたぐので、横の位置を覚えて隣の行で当たり判定をする。

細部は M3 に入るときにここへ書く。

## M4: `markdown_editor`

```rust
markdown_editor(source)                   // Signal<String> と双方向
    .theme(MarkdownTheme::default())
    .emoji(|name| custom_emoji(name))
```

- `text_editor` に、Markdown から作った装飾を付ける。
- Obsidian と同じく、記号（`**`、`#`、`[]()` など）はキャレットが触れている要素の分だけ見せ、それ以外は隠す。画像、Mermaid、チェックボックスは、キャレットが入るとソースに戻る。
- 打鍵のあとは、変わったブロックだけを解析し直して装飾を作り直す。

## 速さの確かめ方

同じ Markdown を `pulldown-cmark` で HTML にし、GitHub に近い CSS を付けて Chromium で開く（比べるためだけに使う）。Chromium では、`<head>` のスクリプトから、最後のスクリプトで `offsetHeight` を読んでレイアウトさせるまでの時間を測る。HTML の読み込み、DOM、スタイル、レイアウトが入る。こちらは `markdown_view` を作り始めてから、最初のレイアウトと描画が済むまでを測る（`tests/view.rs` の `time_a_long_document`、`MARKDOWN_FILE` で文書を指定する）。幅は約 980 px、リリースビルド。

| 文書 | Chromium | ここ | ここの内訳 |
|---|---|---|---|
| サンプルの 50 回分（48 KB、図なし） | 32〜49 ms | 74〜82 ms | フォント一覧の初期化 15、ノード 11〜18、スタイル 5、レイアウト 40（整形 29） |
| tokio の CHANGELOG.md（195 KB、4963 行） | 79〜87 ms | 133〜167 ms | 同じく、初期化 15 を含む |

まだ 1.5〜2 倍遅い。差のほとんどは文字の整形である（1 回 約 15 µs）。Chromium は単語ごとの整形結果を覚えておく仕組みを持っている。縮める方法は次の段で選ぶ。

- 見えている段落だけを整形し、ほかは高さを見積もる（CSS の `content-visibility: auto`）。最初の絵は文書の長さによらず速くなるが、スクロールで高さが変わることがある。
- 整形を複数のスレッドに分ける。速くなるが、スレッドごとにフォントの情報を持つのでメモリが増える。
- 同じ文字列とスタイルの整形結果を使い回す。

図は 1 つ 0.3〜3 ms で、ワーカーで作るので、最初の絵を遅らせない。

## 分かっている限界

- 表のセルは折り返さない。core に表のレイアウトがないためである。
- 段落の中の `inline` の中身（画像の中の文字など）を選択がまたぐときの順番は正しくない。
- 図はクラシックのテーマだけ。
- `merman` より mermaid.js との違いが大きい（ラベルの位置など）。
- リンクの上で押してから選択を始めると、離したときにリンクが開く。
