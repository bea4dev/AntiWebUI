# 08. スクロール入力と全体設定

タッチパッドの慣性スクロール（キネティックスクロール）と、フレームワーク全体の設定の経路。

## OS ごとの違い

慣性を計算する必要があるのは Wayland（と、おそらく X11）だけで、macOS と Windows は OS が生成する。

| OS | 指の移動 | 指を離した通知 | 慣性の計算 | 指を置いて止める |
|---|---|---|---|---|
| Wayland | `axis` + `axis_source=finger` | `axis_stop` | アプリ | `zwp_pointer_gesture_hold_v1`、または次の `axis` |
| macOS | `NSEvent.phase` | `phase` の終了 | OS（`momentumPhase` 付きで届く） | `momentumPhase` の終了 |
| Windows | DirectManipulation の `RUNNING` | `INERTIA` への遷移 | OS | `INERTIA` からの遷移 |

この差はイベントの `phase` で吸収する。プラットフォーム層は変換だけを行い、スクロールの処理と慣性の計算はコアに置く。

- スクロール位置を持つコアなら、端に着いた時点で止められる。
- 時刻を与えるだけでヘッドレスにテストできる。
- 将来の X11、滑らかなホイールスクロール、`scroll_to` のアニメーションにも使える。

macOS と Windows の摩擦を自前で計算して揃えることはしない。OS 標準の感触から外れるため。

## イベント

```rust
WindowEvent::Scroll {
    position, delta_x, delta_y, modifiers,
    source: ScrollSource, // Wheel | Touchpad | Unknown
    phase: ScrollPhase,
    time: u32,            // ミリ秒。速度の計算に使う
}

pub enum ScrollPhase {
    Single,                 // ホイールなど、区切りのない入力
    Began,
    Moved,
    Lifted { fling: bool }, // 指を離した。true ならコアが慣性を計算する
    Held,                   // 指を置いた: 慣性を止める
    Momentum,               // 慣性による移動
    MomentumEnded,
}
```

`delta` の単位は `source` で決まる。`Wheel` はノッチ数（1.0 で 1 ノッチ）、それ以外は物理ピクセル。コアがここで設定の倍率を掛ける。

| source | 物理ピクセルへの変換 |
|---|---|
| `Wheel` | ノッチ × `wheel_step` × スケール |
| `Touchpad` | delta × `touchpad_factor`（Wayland の `axis` は渡す前に 5 倍） |
| `Unknown` | delta そのまま |

`on_scroll` のハンドラには、変換後の物理ピクセルと `source` / `phase` を渡す。自前の慣性でも OS の慣性でも `Lifted` → `Momentum` … → `MomentumEnded` の順で届くので、アプリは区別しなくてよい。`Held` だけはハンドラに届けない。慣性を止めた結果として `MomentumEnded` が届く。

## ジェスチャの固定（ラッチ）

指を動かし始めた時点でヒットテストし、対象を固定する。以降のイベントと慣性は同じ対象に届く。

- **対象の決め方:** 最初の移動量の向きにまだ動ける、最も内側のスクローラー。端に着いている内側のスクローラーは選ばれず、外側に渡る。
- **固定の効果:** 内容が動いて別のスクローラーがポインタの下に来ても動きは移らない。端に着いても外側へ移らず、外側へ移るのは次のジェスチャから。
- **`Single`:** 区切りが無いので固定せず、イベントごとに対象を選ぶ。

## 端数の持ち越し

スクロール位置は整数（[01](01-pixel-model.md)）なので、移動量の端数はスクローラーごとに持ち越す。捨てると、ゆっくり動かしたときに進まず、慣性の終わり際も止まって見える。端に着いたら端数は捨てる。

## 慣性の計算

### 指の移動量

Wayland の `axis` の値は論理ピクセルだが、そのままでは指の動きに対して遅い。Wayland バックエンドは `AXIS_MOTION_GAIN`（5.0）倍して渡す。

| | `axis` 1 あたりの移動量（Chrome と Firefox は実測、CSS px） |
|---|---|
| Chrome 155（`WaylandUnscaledTouchpadScrolling` 有効）、GTK4 | 2.5 |
| Firefox | 4.0 |
| AntiWebUI | 5.0 |
| Chrome 155（既定） | 12.0 |

ブラウザと完全に揃えることは目標にしていない。値は実機の感触で決めた暫定のもの。Chrome の新しい換算に揃えた 2.5 倍は遅く、6 倍は速すぎた。Chrome の既定の 12 倍は、コンポジタの倍率（ShojiWM の `scrollFactor` など）で下げる前提の値。

### 速度

直近 3 フレームの位置を時刻に最小二乗法で当てはめる（Chromium と同じ）。

- 最後の入力から指を離すまで 200 ms 以上空いたら、慣性を始めない。速く動かして止め、少し待ってから離したときに飛ばないようにするため。
- 慣性の初速は、指の下の内容の速さの 0.4 倍（`FLING_SPEED_RATIO`）。Chrome の新しい換算（移動は 2.5 倍、初速は `axis` の速度そのまま）と同じ比率。`touchpad_factor` は初速にも掛かる。
- `wl_pointer` の時刻はミリ秒なので、同じ時刻のサンプルしか無いときは慣性を始めない。

### 曲線

Chromium の `PhysicsBasedFlingCurve` と同じ。位置を時刻の関数として求めるので、フレーム落ちで動きがずれない。論理ピクセルで計算する（スケールが違っても同じ感触にするため）。

```
距離   d = min(v² / (2a), ウィンドウの大きさ × 3 × 加速の倍率)    軸ごと
時間   T = min(v / 2300, 2 秒)                                    速いほうの軸
位置   x(t) = d × cubic-bezier(p1, 0.55, 1.0)(t / T)
```

- `a` は `kinetic.deceleration`（2645.7 px/s²、96 ppi × Chromium の物理定数）。
- `p1` は `(0.2, 1.0)` を基準に、曲線の初速が指の速度と一致するように調整する。
- 開始時刻は指を離した時刻ではなく最後の移動の時刻。そこから連続して動くように。

### 連続フリックの加速

慣性の途中で同じ向きにもう一度フリックすると、前の速度に足される（Chromium の `FlingBooster`）。連続して弾くほど速くなり、上限も同じ比率で伸びる。

足されるのは次の条件をすべて満たすとき。

- 指が戻ってから、または最後の移動から 50 ms 以内に次の移動が来ている。
- 向きが同じ（内積が正）。
- 指の移動が 150 px/s 以上。
- 指が戻った時点の慣性の速さと、新しいフリックの速度がどちらも 350 px/s 以上。

ボタンやキーなど、指以外の理由で慣性を止めたときは足さない。

### 止まる条件

| 条件 | 備考 |
|---|---|
| 曲線の終わり | |
| 端に着いた | 不要なフレームを出さない |
| 次の指の移動（`Began` / `Moved`）、`Single` | |
| `Held` | コンポジタが `zwp_pointer_gestures_v1` を持つ場合のみ届く |
| ボタンを押した、キーを押した | libinput の推奨 |
| ポインタが 8 論理 px 以上動いた | 2 本の指を同時に離せず 1 本が残ったときの小さな動きでは止めない |
| ポインタがウィンドウから出た | |
| 対象のノードが消えた | |

止まると、OS が送り続ける `Momentum` も次のジェスチャまで無視する。

### フレームの駆動

```
loop {
    ui.animate(now)    // 慣性を進める（スクロールが動くだけで、以降は通常のスクロールと同じ）
    ui.update()
    paint / present
    if ui.animating() { 次のフレームを要求 }
}
```

- フレームコールバックに合わせて進むので、慣性中も画面の更新頻度を超えて描かない。止まれば要求もやめる。
- 整数ピクセル未満しか動かなかったフレームは何も提示しない。その場合はコールバックが来ないので、数ミリ秒後にもう一度進める。

### 効果

`bench_changes`（1620×1616、Radeon 880M）で速い慣性を流すと、1 フレームあたり 0.31 ms（20000 行）。実際のウィンドウ（900×1616）に 3333 px/s の慣性を流した計測では、平均 0.19 ms で、画面の更新（約 120 Hz）に合わせて約 0.8 秒間進んで止まった。止まったあとのフレームは無い。

### 正しさの確認

- `tests/kinetic.rs`: ジェスチャの固定、端数、慣性の開始と停止、設定、ハンドラ、OS 由来の慣性を合成イベントで確認する。
- `tests/incremental.rs`: ランダムな操作に慣性を混ぜ、差分更新が全部やり直した結果と一致することを確認する。
- `tests/render.rs`: 慣性の各フレームのレイヤーキャッシュの描画が、毎回描き直した結果とピクセル単位で一致することを確認する。
- `anti-webui-wayland` の単体テスト: `wl_pointer` のフレームからの変換を確認する。
- わざとバグを入れて検出できることを確認した。
- 実機のタッチパッドは自動では試せない。実際のウィンドウで `Runner` にイベントを注入して確認した範囲は、慣性のあとの画面が全面描画と一致すること（差 0 ピクセル）まで。

### Chrome との比較

Smithay の `smallvil` に `wl_pointer` のイベント列を流す処理を足した小さなコンポジタで Chrome を動かし、`window.scrollY` を記録した（Chrome 155、`WaylandUnscaledTouchpadScrolling` 有効）。同じイベント列を Chrome と同じ 2.5 倍で `tests/kinetic.rs` からコアに流し、曲線と加速が一致することを確認している。実際の倍率は 5 倍なので、同じ指の動きで進む距離は下の表のおよそ 2 倍（1.8〜2.5 倍）になる。

| 入力（`axis` の速度、8 ms ごと） | Chrome | AntiWebUI |
|---|---|---|
| 3 × 100 フレーム（慣性なし） | 750 | 750 |
| 200 px/s × 25 フレーム | 107 | 差 5 px 以内 |
| 1000 px/s × 25 フレーム | 689 | 差 5 px 以内 |
| 2000 px/s × 25 フレーム | 1752 | 差 5 px 以内 |
| 3000 px/s × 25 フレーム（上限に到達） | 2900 | 差 5 px 以内 |
| 12000 px/s × 25 フレーム | 7400 | 差 5 px 以内 |
| 2000 px/s × 12 フレームを 3 連続（加速あり） | 6928 | 6953 |
| 1000 px/s × 12 フレームを間隔を空けて 3 回（加速なし） | 1284 | 1287 |

ウィンドウの高さを変えると上限が高さの 3 倍で変わること、スケール 2 でも CSS px で同じ値になることも確認した。AntiWebUI 自体はこのコンポジタで表示できないので（dmabuf が無い）、`wl_pointer` からの変換は単体テストで別に確認している。

## 全体設定

```rust
App::new()
    .settings(|s| {
        s.scroll.touchpad_factor = 1.5;
        s.scroll.wheel_step = 64.0;
        s.scroll.kinetic.deceleration = 2000.0;
    })
    .run(root)?;

// 実行中の変更。signal なので、読んでいる UI も追従する
button("速く").on_click(|_| update_settings(|s| s.scroll.touchpad_factor *= 1.25));
text(|| format!("倍率: {}", settings().scroll.touchpad_factor));
```

- 構造体は `#[non_exhaustive]` で、クロージャで変更する。項目を増やしても既存コードが壊れない。
- 中身は 1 つの `Signal<Settings>`（スレッドローカル、`Document` と同じ単位）。変更は稀なので、項目ごとに分けない。
- 設定は次のイベントから効く。進行中の慣性は開始時の値で走り切る。

| 設定 | 既定値 | Wayland | macOS / Windows |
|---|---|---|---|
| `scroll.touchpad_factor` | 1.0 | 有効 | 有効（慣性分にも掛かる） |
| `scroll.wheel_step` | 48.0（論理 px / ノッチ） | 有効 | 有効 |
| `scroll.kinetic.enabled` | true | 有効 | 有効（OS の慣性を捨てる） |
| `scroll.kinetic.velocity_factor` | 1.0 | 有効 | 無効 |
| `scroll.kinetic.deceleration` | 2645.7（論理 px/s²） | 有効 | 無効 |
| `scroll.kinetic.max_screens` | 3.0（ウィンドウの大きさの倍数） | 有効 | 無効 |
| `rendering.frame_advance` | `Auto`（[10](10-frame-pacing.md)） | 有効 | 未実装 |

今は開発者が指定する設定だけを持つ。利用者が全アプリに効かせる設定ファイルは、将来この下の層として足せる。キャレットの点滅やダブルクリックの間隔も、必要になれば同じ経路に移す。
